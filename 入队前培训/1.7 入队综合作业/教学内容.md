# 1.7 入队综合作业

> 本节目录 / 建议课时：45 分钟（任务书讲解 30 + 答疑 15）｜前置要求：1.1~1.6 全部完成

恭喜你走到入队前培训的最后一站。从这一节开始，**没有老师一步步带你了**——你将拿到一份任务书，然后独立完成一个小型控制系统。

别慌，这不是考试刁难你。入队作业的真实目的是：**把你 1.1~1.6 学到的所有零件，组装成一台你自己能讲明白的机器**。作业的结果重要，但你「能解释、会定位、讲得清」的过程更重要。

## 作业目标

- [ ] 读懂任务书，能说出自己要交什么、什么时候交、怎么交
- [ ] 独立完成「输入 → 控制逻辑 → 执行器 → 反馈」的完整闭环系统
- [ ] 能画出自己系统的数据流图，并解释图上每一个环节
- [ ] 会用「现象 → 假设 → 验证」的方法独立定位基本问题
- [ ] 会查资料：官方资料站、手册、开源项目、提问
- [ ] 合理使用 AI：全程记录 AI 的使用方式，提交前能解释每一行关键代码
- [ ] Git 小步提交、提交信息规范、有 `.gitignore`，历史能讲出开发过程
- [ ] 系统连续稳定运行，异常情况有处理

## 作业任务书

### 总览

用 2 周时间，独立完成一个**小型控制任务**。任务必须包含四个环节：

```
  输入（按键 / 其他输入设备）
        │ 目标值
        ▼
  控制逻辑（状态判断 + PID）
        │ 控制量（电流 / 电压）
        ▼
  执行器（电调 + 电机）──────► 反馈（编码器）┐
        ▲                                     │
        └──────────── 实际角度 / 转速 ◄────────┘
```

也就是 1.4 节那张图的完整版：**STM32 → CAN → 电调 → 电机 → 编码器 → STM32**，再加上 1.5 的 PID 和 1.6 的 Git 与 AI。

三个可选方向（任选其一）：

| 方向 | 一句话任务 | 难度 |
|---|---|---|
| A. 电机速度闭环控制器 | 输入设定目标转速，PID 闭环跟踪并实时显示 | ★★★ 推荐 |
| B. 简单单轴云台 | 输入设定目标角度，PID 保持云台角度稳定 | ★★★★ |
| C. 自选小任务 | 任何难度相当的「输入→逻辑→执行→反馈」闭环 | ★★★★ |

> 一句话总结：**作业 = 一个你能从键盘讲到底盘的完整小闭环，外加一份规范的过程记录。**

## 可选方向详解

### 方向 A：电机速度闭环控制器（推荐）

**任务描述**：在 1.4/1.5 的电机平台上，做一台「可设定转速的恒速转台」：用按键（或电位器等输入设备）设定目标转速，STM32 通过 PID 速度闭环驱动电机（M3508/M2006 均可）稳定跟踪目标，并通过串口（或显示模块）实时打印「目标转速 / 实际转速」。系统要有基本异常处理：目标限幅、输出限幅、电机离线检测。

**建议拆分步骤（三个里程碑）**：

- **里程碑 1：最小闭环**——电机转起来、编码器读数正确、PID 速度闭环跟踪恒定目标。
  - 做法：把 1.4 的「读反馈 + 发控制量」和 1.5 的 `PID_Calc()` 接成一个环；先固定目标值（如 1000 RPM，数值按你手上电机的安全范围取），调出「阶跃后快速跟上、无明显振荡」的参数。
  - 自查点 ✔：目标从 0 阶跃到 1000 RPM，实际转速 3 秒内进入 ±5% 误差带且不持续振荡。
- **里程碑 2：输入与显示**——加输入设备改目标值，加显示看实况。
  - 做法：按键短按 +500 / 长按清零（或用电位器，讲解时按战队现有硬件演示）；串口定时打印 `目标 | 实际 | 误差`。
  - 自查点 ✔：运行时改目标，电机平滑变速；串口数字和肉眼看转速对得上。
- **里程碑 3：健壮性与收尾**——异常处理 + Git 整理 + 文档。
  - 做法：目标限幅（超出安全范围截断）、输出限幅（PID 输出截断）、电机离线检测（反馈超时报警并停止输出）；整理 Git 历史，写 README，录视频。
  - 自查点 ✔：拔掉电机 CAN 线，程序报警且不发失控指令；重新上电功能一致。

**涉及知识点对照**：

| 作业环节 | 用到的知识点 | 来自 |
|---|---|---|
| 环境与工具链 | 编译、烧录、调试 | 1.1 |
| 控制逻辑 | 变量、判断、循环、函数、结构体（PID 结构体） | 1.2 |
| 定时调度 | Timer、中断（控制周期） | 1.3 |
| 输入 | GPIO 按键读取 | 1.3 |
| 通信 | CAN 收发 | 1.3、1.4 |
| 执行器与反馈 | 电调、电机、编码器、控制量 / 反馈量 | 1.4 |
| 闭环控制 | Target / Current / Error、P / I / D | 1.5 |
| 过程管理 | Git 提交、`.gitignore`、AI 辅助 | 1.6 |
| 异常处理 | 限幅、超时检测 | 本节新增（2.9 会深入） |

**验收标准（可测量）**：

1. 目标转速在安全范围内任意设定（如 -3000 ~ +3000 RPM，按你手上电机的安全范围取），实际转速**稳态误差 ≤ ±5%**（对 1000 RPM 即 ±50 RPM 以内）；
2. 0 → 1000 RPM 阶跃，**3 秒内**进入 ±5% 误差带，无持续振荡；
3. 运行时改目标，电机平滑变速，不出现瞬间满功率冲击；
4. **连续运行 ≥ 5 分钟**无异常；断电重启后表现一致；
5. 拔掉电机 CAN 线，程序能检测离线、报警并停止输出，插回后能恢复。

### 方向 B：简单单轴云台（Pitch 轴）

**任务描述**：做一条单轴（Pitch 俯仰轴）云台：以编码器（或 IMU）角度为反馈，用 PID 位置环把云台稳定在目标角度；用按键（或电位器）设定目标角度；具备角度限位保护。你可以用 GM6020（内置绝对编码器，直驱云台）或 M2006 + C610 + 编码器，按战队现有硬件选。

**建议拆分步骤（三个里程碑）**：

- **里程碑 1：角度反馈**——把角度读准。
  - 做法：读取编码器（或 IMU）角度，串口打印；手动转动云台，观察数字变化是否与实际转动的角度一致（方向、量程、零点）。
  - 自查点 ✔：手动转 30°，读数变化约 30°；转到两端不跳变。
- **里程碑 2：位置闭环**——PID 角度环稳住。
  - 做法：`PID_Calc()` 的 Target 换成角度、Current 换成角度反馈；先只调 P，再视情况加一点 D 抑制震荡（角度环通常不需要 I，或有专门处理，讲解时说明）。
  - 自查点 ✔：目标 ±30° 阶跃，快速到位、无明显振荡；手动掰动后自动回位。
- **里程碑 3：输入与保护**——设定角度可调，限位保护生效。
  - 做法：按键加/减目标角度（单次 ±5°）；超出 ±60° 的目标被截断；检测到角度异常（如超出机械限位）停止输出；整理 Git、README、视频。
  - 自查点 ✔：设定 ±90° 时被截到 ±60°；连续运行 5 分钟不漂移。

**涉及知识点对照**：

| 作业环节 | 用到的知识点 | 来自 |
|---|---|---|
| 环境与工具链 | 编译、烧录、调试 | 1.1 |
| 控制逻辑 | 变量、判断、循环、函数、结构体 | 1.2 |
| 定时调度与输入 | Timer、中断、GPIO 按键 | 1.3 |
| 通信 | CAN 收发 | 1.3、1.4 |
| 执行器与反馈 | GM6020/M2006、编码器、IMU 与 Yaw/Pitch | 1.4 |
| 闭环控制 | 位置环 PID、超调与震荡 | 1.5 |
| 过程管理 | Git、AI 辅助 | 1.6 |
| 异常处理 | 角度限幅、限位保护 | 本节新增 |

**验收标准（可测量）**：

1. 目标角度在 **-60° ~ +60°** 内任意设定，到位**误差 ≤ ±2°**，**无震荡**（观察不到持续抖动）；
2. 手动掰动云台约 30° 后松手，**1 秒内**回到目标角度并稳定；
3. 设定目标超出 ±60° 时被截断到限位值，电机不发生撞击机械限位；
4. **连续运行 ≥ 5 分钟**角度不漂移；断电重启表现一致；
5. 出现异常（如反馈超时）时停止输出，不出现失控转动。

### 方向 C：自选小任务

**任务描述**：任何难度与 A/B 相当的小型控制任务，但**必须**包含完整的「输入 → 控制逻辑 → 执行器 → 反馈」闭环，且至少含 PID 或等价的反馈控制。参考例子（不必照抄）：

- **恒温小风扇**：温度传感器（反馈）+ PWM 风扇（执行器）+ 设定温度（输入）+ PID 温控；
- **LED 亮度恒定**：光敏传感器 + LED + PID 恒定照度（在环境光变化时保持亮度）；
- **舵机角度控制**：舵机 + 电位器/编码器反馈 + 位置环（适合没有 RoboMaster 电机的同学）。

**要求**：

1. 开工前先写一份 **200 字方案说明**（做什么、输入/执行/反馈各是什么、验收标准怎么量），提交给带教确认（提交方式：讲解时公布）；
2. 里程碑同样按「1 最小闭环 → 2 输入显示 → 3 保护收尾」拆分；
3. 验收标准**必须可测量**（数字 + 时间），不能写「效果好」。

**涉及知识点对照**：与 A/B 同框架——1.1 环境、1.2 C 语言、1.3 单片机、1.5 PID、1.6 Git/AI 全部覆盖；1.4 视具体执行器而定（用其他电机/舵机/风扇的，按对应资料自学，这本身就是「查资料」能力的考察）。

## 考察点逐条解释

### 考察点 1：是否理解自己的代码

**及格线：能画出系统的数据流图，并解释图上每一个环节。**

画数据流图时，每个环节至少能回答三个问题：**数据是什么**（类型、单位、取值范围）、**从哪来往哪去**、**多久更新一次**。例：

```
按键 ──目标转速 int16(rpm)──► 控制逻辑 ──控制量 int16──► 电调+电机
                                 ▲        (每 1ms 更新)       │
                                 │                            ▼
                         编码器转速 ◄── CAN 反馈帧 ────── 编码器
                         (每 1ms 更新)
```

更硬核的检验：让带教**随机指着你代码里的任意一行**，你能说清它干什么、为什么要这么写。「这段是我抄的/ AI 写的，我不清楚」——这一行就是你的作业漏点。

> 一句话总结：**讲得清每一行的代码才是你的代码，讲不清的部分都是隐患。**

### 考察点 2：能否解释系统数据流

能完整叙述一次动作的「一镜到底」：按下按键后，信号如何变成按键状态 → 目标值如何更新 → PID 如何算出控制量 → CAN 帧如何发出去 → 电机如何转 → 编码器如何回报 → 下一次计算如何用到回报值。就像能背出「你点了一杯奶茶后，从下单到出品奶茶店的完整动线」。

时间尺度也要有概念：**1 秒内这套循环跑了多少次**（1 kHz 就是 1000 次），哪个环节最慢、哪里可能被阻塞。

### 考察点 3：能否独立定位基本问题

及格线：遇到问题按 **「现象 → 假设 → 验证 → 缩小范围」** 四步走，而不是乱试。比如「电机不转」：

```
现象：上电后电机不转，串口无输出
假设①：程序没跑起来 → 验证：加个 LED 心跳，发现灯在闪，排除
假设②：CAN 没初始化成功 → 验证：打印 CAN 初始化返回值，发现错误码
假设③：波特率/线序问题 → 验证：按错误码查手册对应项，确认
```

工具用起来：Keil Debug（断点、Watch）、串口打印、万用表。**每排除一个假设，就缩小一圈范围。**

### 考察点 4：能否查找资料

会查三样东西：**官方资料**（RoboMaster 官方资料站、电机/电调手册）、**开源项目**（往届战队开源、GitHub）、**问答与文档**（报错原文搜索、提问）。查到的资料要「消化」：不是复制粘贴，而是能用自己的话转述「它说了什么、我用了哪部分」。

### 考察点 5：是否合理使用 AI

两件事：**记录** + **解释**。

- **记录**：作业报告里写清 AI 的使用方式——哪一步用了（读代码 / 查资料 / 解报错 / 改代码）、问了什么、AI 给了什么、你采纳/否决了什么。
- **解释**：提交前（答疑时）能解释**每一行关键代码**。AI 可以写，但解释责任在你。

红线只有一条：**AI 生成 → 能编译 → 直接交**。能跑但讲不清，等于没做。

> 一句话总结：**AI 用得越多，你的解释义务就越大；记录 + 解释，缺一不可。**

### 考察点 6：Git 使用是否规范

- **小步提交**：一次 commit 一件事，整个作业 ≥10 次有意义提交（「有意义」= 提交信息看得出改了什么）；
- **信息规范**：`feat: 添加按键调速功能` 这种格式，杜绝 `更新`、`111`、`asdf`；
- **有 `.gitignore`**：`Objects/` 等编译产物不入库；
- **历史可读**：`git log` 从头到尾能看出你的开发过程——这也证明你不是最后一天复制粘贴的。

### 考察点 7：系统能否稳定运行

「调通一次」和「稳定运行」是两回事。稳定运行的最低标准：

- 连续运行 ≥5 分钟无异常；
- 反复断电重启，表现一致；
- 制造异常（拔线、乱按、目标给极端值）系统不失控——要么处理，要么报警。

## 推荐开发节奏（六步）

```
① 画系统框图 ──► ② 搭最小闭环 ──► ③ 加输入与显示 ──►
④ 加保护与异常处理 ──► ⑤ 整理 Git 记录 ──► ⑥ 写 README + 录视频
```

1. **画系统框图**：先在纸上（或白板）画好数据流图，标出每个环节的数据类型和周期。画不清楚就别开工——图都画不出来，代码一定糊。
2. **搭最小闭环**：只做「反馈 → PID → 执行器」，目标值先写死。这是整个作业的地基，地基稳了再盖楼。
3. **加输入与显示**：让目标值可调，让数据可见（串口打印）。「看不见的系统没法调」。
4. **加保护与异常处理**：限幅、超时检测、失控保护。放在功能完成之后、测试之前。
5. **整理 Git 记录**：回看 `git log`，检查提交信息是否规范、`.gitignore` 是否生效、历史能否讲出开发故事。
6. **写 README + 录视频**：README 按「功能 → 框图 → 数据流 → 运行方法 → 问题记录」写；视频一镜到底拍核心功能。

> 一句话总结：**先画图，后搭环，再添砖；先能跑，后能稳，最后补文档。**

| 1 | 抄 AI 代码不验证 | 代码能跑，被问一行就卡壳 | 用 1.6 的「必须动作清单」：diff 逐行审 → 编译 → 实机验证 |
| 2 | Git 一次提交全部代码 | 历史只有 `first commit: 全部完成` | 小步提交，完成一个功能就 commit 一次 |
| 3 | 只调通一次就交 | 演示时重启一次就翻车 | 连续运行 5 分钟 + 反复断电重启测试 |
| 4 | 不会描述问题 | 只喊「电机不转」 | 按提问模板带齐现象/期望/已尝试/数据 |
| 5 | 只调参数不理解参数 | 说不出 Kp 变大为什么震荡 | 每次改参数记下现象，回看 1.5 概念 |
| 6 | 拖到最后三天 | 2 周节奏崩掉，只能抄 | 按 D1~D14 建议节奏走，D14 是缓冲日 |
| 7 | 不写 README / 不录视频 | 交付物不齐 | 把交付物清单当 checklist 逐项打勾 |

## 答疑提问模板

答疑时（问带教、问队友、问 AI 通用），按四要素 + 一个猜测来提问：

```
【现象】电机上电后不转，串口无输出（要具体、可复现）
【期望】上电后能以 1000 RPM 恒速旋转
【已尝试】1. 检查 CAN 线序 ✔  2. 换了一个电机 ✗ 仍不转
          3. 加打印：CAN 初始化返回错误码 0x03
【数据/截图】串口日志截图 + 接线照片 + 报错原文
【我的猜测】怀疑 CAN 波特率配置不匹配
```

- **现象**：描述你看到了什么，而不是你的结论（写「电机不转」，别写「电机坏了」）；
- **期望**：你希望发生什么；
- **已尝试**：你已经做过哪些排查（证明你动过脑子，也避免别人重复）；
- **数据/截图**：日志、报错原文、照片——一张截图胜过一百个字；
- **我的猜测**（选填）：你的假设，答的人可以顺着你的思路纠正。

提问前先自查三步：**先看报错原文 → 先查资料 → 先复现一次**。三样都做了还解决不了，再按模板提问。

> 一句话总结：**会提问 = 现象 + 期望 + 已尝试 + 数据截图，再加一个自己的猜测。**

## 常见问题与排查（关于作业本身）

| 现象 | 可能原因 | 处理办法 |
|---|---|---|
| 不知道选哪个方向 | 三个方向都了解得不具体 | 没把握选 A（最扎实）；对云台感兴趣选 B；有想法先写 200 字方案再选 C |
| 2 周时间不够用 | 卡在环境/老代码跑不通 | 前 2 天务必确认 1.4/1.5 的工程能编译烧录；卡住立刻问，别自己耗 |
| 电机一上电就疯转 | PID 输出未限幅、方向接反、反馈没读到 | 先做里程碑 1 的「开环最小电流」验证，再上闭环；输出限幅先加上 |
| 目标改了电机没反应 | 输入没读对、目标没更新到 PID | 串口打印输入值和目标值，二分定位是「没读到」还是「没用到」 |
| 串口打印乱码 | 波特率不匹配、编码问题 | 核对串口助手波特率；优先打印英文和数字 |
| commit 太多太碎 / 太少 | 没有按功能粒度拆分 | 以「里程碑内的一个功能点」为粒度：完成且验证过，才 commit |
| 视频拍不出稳定运行 | 只演示了「运气最好的一次」 | 先做连续运行测试，通过后再拍；一镜到底不剪辑反而可信 |
| 报告里的 AI 记录不知道写什么 | 没养成随手记的习惯 | 每次问完 AI 立刻记一句：问了什么、采纳了什么、为什么 |

## 交作业前自检

1. 我的系统数据流图里，每个环节都能说出「数据类型 + 单位 + 更新周期」吗？
2. 带教随机指我代码里任意一行，我都能解释吗？
3. 拔掉电机 CAN 线（或断开反馈），我的系统会报警并停止输出，而不是失控吗？
4. 目标给到极端值（最大/最小/快速反复切换），系统有对应的限幅处理吗？
5. `git log --oneline` 的历史 ≥10 次，且每次信息都符合「类型: 简述」吗？
6. 我的 `.gitignore` 生效了吗（编译产物没有进仓库）？
7. README 里写清楚「功能、框图、数据流、怎么运行、遇到的问题」了吗？
8. 视频里展示的是连续稳定运行，而不是「唯一成功的一次」吗？

<details>
<summary>参考答案</summary>

1. 数据流图的标准：每个箭头都标出数据名、类型（如 `int16`）、单位（如 rpm）、方向、更新周期（如 1 ms）。任何一个箭头说不全，说明这一环还没「吃透」。
2. 解释不出来 = 这行代码不是你的。回去读、问 AI 解释、做实验验证，直到能讲清为止。
3. 反馈超时检测（如 100 ms 没收到反馈帧 → 停止输出并报警）是方向 A/B 验收标准的硬性要求，自检时一定要做。
4. 输入极端值 → 目标限幅；计算极端值 → 输出限幅。两道限幅都在，极端操作才不失控。
5. 小步提交的粒度：「完成一个功能点且验证通过」= 一次 commit。历史能讲出开发故事，才算合格。
6. `git status` 里不应出现 `Objects/`、`Listings/` 等目录；已误提交的用 `git rm -r --cached` 移出跟踪。
7. README 五要素：功能 / 框图 / 数据流 / 运行方法 / 问题记录。缺一个，看的人（和未来的你）就要猜。
8. 演示前先做「连续运行 + 断电重启」测试，通过后再录；一镜到底的真实稳定比剪辑的完美更可信。

</details>
