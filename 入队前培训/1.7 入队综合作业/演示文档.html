1.7　入队综合作业

入队综合作业

独立完成一个闭环控制小任务，两周交卷
电控组长 董心宇

本节地图：作业全景

任务书

2 周完成一个闭环小任务；交付物 4 样：视频、Git 仓库、README、一页报告

三个方向

A 电机速度闭环（推荐）；B 简单单轴云台；C 自选小任务。均按里程碑 1/2/3 推进

抄 AI 不验证、一次提交全部、只调通一次、不会描述问题、拖到最后三天

推送战队指定平台；仓库地址与截止时间以通知为准（讲解时公布）

任务书：作业是什么

入队综合作业＝在 2 周内独立完成一个「输入 → 控制逻辑 → 执行器 → 反馈」完整闭环的小型控制任务， 检验 1.1~1.6 全部内容的独立运用能力。系统必须包含：STM32、输入设备、执行器、反馈、基本控制逻辑、PID（或等价反馈控制）、Git、基本异常处理。 

输入(按键) ──目标值──► 控制逻辑(状态+PID) ──控制量──► 执行器(电调+电机)
     ▲                                                     │
     └──────────── 反馈帧(编码器 角度/转速) ◄───────────────┘
（即 1.4 的「STM32 → CAN → 电调 → 电机 → 编码器 → STM32」＋ 1.5 的 PID ＋ 1.6 的 Git/AI）

功能完整 ≠ 合格：能跑只是起点，讲得清每一环才算理解。

过程与结果同样计分：Git 历史、排查记录、AI 使用记录都是交付物。

这是 1.1~1.6 的「结业考」，也是你第一次独立开发。

任务书：两周怎么用

建议节奏（D = 第几天）

时间该做什么完成标志
D1~2画系统框图、复习 1.4/1.5 代码、确认环境框图完成，老代码跑通
D3~5里程碑 1：最小闭环电机按目标稳定转
D6~7里程碑 2：输入 + 显示改目标、看得到数据
D8~10里程碑 3：异常处理拔线、重启不失控
D11~12长时间测试 + 修 bug连续跑 5 分钟以上
D13整理 Git、写 README、录视频交付物齐
D14缓冲日，提前交不卡死线

红线：最后三天才开工 = 高频翻车（只能抄）。节奏是建议，但 D14 必须留作缓冲。

提交方式：把 Git 仓库推送到战队指定平台，并提交仓库地址与视频链接。（平台地址与截止时间：讲解时由战队统一公布。）

组队与硬件：作业独立完成；硬件与设备借用方式按战队安排（讲解时说明）。

三个方向，任选其一

方向任务一句话难度验收核心（可测量）
A 电机速度闭环控制器 设定目标转速，PID 闭环跟踪并实时显示 推荐 ±5% 速度跟踪、3 秒内稳定、连续 5 分钟
B 简单单轴云台（Pitch） 设定目标角度，PID 位置环稳定云台 中等 ±60° 内无震荡、误差 ≤2°、掰动后回位
C 自选小任务 任何难度相当的闭环小任务 中等 自拟且可测量，先交 200 字方案

选择建议：没把握选 A（最扎实，直接复用 1.4/1.5 成果）；对云台感兴趣选 B；有想法选 C，但必须先写方案与带教确认。

三个方向共用同一骨架：里程碑 1 最小闭环 → 里程碑 2 输入与显示 → 里程碑 3 保护与收尾。

方向 A：电机速度闭环控制器

任务描述：在 1.4/1.5 的电机平台上做一台「可设定转速的恒速转台」——用按键（或电位器）设定目标转速， STM32 通过 PID 速度闭环驱动电机（M3508 / M2006 均可）稳定跟踪，串口实时打印「目标 / 实际 / 误差」； 含目标限幅、输出限幅、电机离线检测。

方向 A：里程碑与验收标准

三个里程碑

里程碑内容与自查点
1 最小闭环读反馈 + 发控制量 + PID_Calc 接成环；目标写死（如 1000 RPM）。自查：0→1000 阶跃 3 秒内进 ±5% 带、无持续振荡
2 输入与显示按键短按 ±500、串口打印 目标|实际|误差。自查：运行时改目标平滑变速、数字与实测一致
3 保护与收尾目标/输出限幅、离线报警停输出、整理 Git、README、视频。自查：拔 CAN 线报警不失控、重启一致

验收标准（全部可测量）

  1. 安全范围内任意设定目标，实际转速稳态误差 ≤ ±5%（对 1000 RPM 即 ±50 RPM）；
  2. 0 → 1000 RPM 阶跃，3 秒内进入 ±5% 误差带，无持续振荡；
  3. 运行时改目标，平滑变速，不出现瞬间满功率冲击；
  4. 连续运行 ≥5 分钟无异常；断电重启后表现一致；
  5. 拔掉电机 CAN 线，程序检测离线、报警并停止输出，插回后恢复。

方向 B：简单单轴云台（Pitch）

任务描述：以编码器（或 IMU）角度为反馈，PID 位置环把云台稳定在目标角度；按键（或电位器）设定目标；含角度限位保护。 硬件可选 GM6020（内置绝对编码器、直驱）或 M2006 + C610 + 编码器，按战队现有硬件选。

三个里程碑

里程碑内容与自查点
1 角度反馈读编码器/IMU 角度并打印。自查：手转 30° 读数变化约 30°，两端不跳变
2 位置闭环先调 P，再视情况加 D 抑制震荡。自查：±30° 阶跃到位无震荡、掰动后自动回位
3 输入与保护按键 ±5° 步进、超 ±60° 截断、异常停输出。自查：设 ±90° 被截到 ±60°

验收标准（全部可测量）

  1. 目标角度在 -60° ~ +60° 内任意设定，到位误差 ≤ ±2°，无震荡；
  2. 手动掰动约 30° 后松手，1 秒内回到目标并稳定；
  3. 目标超出 ±60° 被截断到限位值，不撞击机械限位；
  4. 连续运行 ≥5 分钟角度不漂移；断电重启一致；
  5. 反馈超时等异常出现时停止输出，不失控转动。

知识点：1.4 的 IMU 与 Yaw/Pitch、编码器；1.5 位置环（角度环通常少用 I，讲解时说明）。

方向 C：自选小任务

硬性要求

  • 必须包含「输入 → 控制逻辑 → 执行器 → 反馈」完整闭环；
  • 至少含 PID 或等价的反馈控制；
  • 开工前写 200 字方案（做什么、输入/执行/反馈各是什么、验收标准怎么量），提交带教确认；
  • 验收标准必须可测量（数字 + 时间），不能写「效果好」。

参考例子（不必照抄）

题目反馈 / 执行器 / 控制
恒温小风扇温度传感器 + PWM 风扇 + PID 温控
恒照度 LED光敏传感器 + LED + PID 恒定照度
舵机角度控制舵机 + 电位器反馈 + 位置环

用其他执行器（舵机 / 风扇等）的按对应资料自学——这本身就是「查资料」考察项的一部分。

考察点 1/2：理解代码与解释数据流

1 · 是否理解自己的代码

及格线：能画出系统数据流图，并解释图上每一个环节——每个环节回答三问：数据是什么（类型、单位、取值范围）、从哪来往哪去、多久更新一次。

硬核检验：带教随机指着代码里任意一行，你能说清它干什么、为什么这么写。「这段是 AI 写的，我不清楚」= 漏点。

2 · 能否解释系统数据流

一镜到底：完整叙述按下按键后——信号如何变成按键状态 → 目标值如何更新 → PID 如何算出控制量 → CAN 帧如何发出 → 电机如何转 → 编码器如何回报 → 下一次计算如何用到回报值。

时间尺度：1 kHz 控制周期 = 每秒 1000 次循环；要清楚哪个环节最慢、哪里可能被阻塞。

考察点 3/4：定位问题与查资料

3 · 能否独立定位基本问题

四步法：现象 → 假设 → 验证 → 缩小范围。示例「电机不转」：

  • 假设① 程序没跑 → 加 LED 心跳，灯在闪，排除；
  • 假设② CAN 初始化失败 → 打印初始化返回值，出现错误码；
  • 假设③ 波特率 / 线序 → 按错误码查手册对应项，确认。

工具：Keil Debug（断点、Watch）、串口打印、万用表。每排除一个假设，缩小一圈范围。

4 · 能否查找资料

会查三类资料：

  • 官方资料：RoboMaster 资料站、电机 / 电调手册；
  • 开源项目：往届战队开源、GitHub 仓库；
  • 问答与文档：报错原文搜索、按模板提问。

消化：查到的资料要能用自己的话转述「它说了什么、我用了哪部分」，不是复制粘贴。

考察点 5/6：合理用 AI 与 Git 规范

5 · 是否合理使用 AI

两件事：记录 + 解释。

  • 记录：哪一步用了 AI、问了什么、AI 给了什么、你采纳/否决了什么，写进报告；
  • 解释：提交前能解释每一行关键代码——AI 可以写，解释责任在你。

红线：AI 生成 → 能编译 → 直接交。能跑但讲不清 = 没做。

6 · Git 使用是否规范

  • 小步提交：一次 commit 一件事，全程 ≥10 次有意义提交；
  • 信息规范：feat: 添加按键调速功能，杜绝「更新」「111」；
  • .gitignore 生效：Objects/ 等编译产物不入库；
  • 历史可读：git log 从头到尾能看出开发过程——证明不是最后一天复制粘贴。

考察点 7：系统能否稳定运行（权重 30%）

调通一次 ≠ 稳定运行

稳定运行的最低标准：

  • 连续运行 ≥5 分钟无异常；
  • 反复断电重启，表现一致；
  • 制造异常（拔线、乱按、极端目标）系统不失控——要么处理，要么报警。

视频里要展示的是连续稳定运行，不是「唯一成功的一次」。

异常处理三件套（加分项）

措施做法
目标限幅输入目标超出安全范围即截断
输出限幅PID 输出截断，防瞬间满功率
反馈超时检测约 100 ms 未收到反馈帧 → 停止输出并报警

超时阈值等参数以你实测为准，此处为参考量级。

推荐开发节奏：六步

① 画系统框图

标出每环数据类型与周期；画不清就别开工——图都画不出来，代码一定糊。

② 搭最小闭环

只做反馈 → PID → 执行器，目标值写死。这是地基，地基稳了再盖楼。

③ 加输入与显示

目标可调、数据可见（串口打印）。看不见的系统没法调。

④ 加保护与异常处理

限幅、超时检测、失控保护。放在功能完成之后、测试之前。

⑤ 整理 Git 记录

回看 log：信息是否规范、.gitignore 是否生效、历史能否讲出开发故事。

⑥ README + 视频

README 五要素：功能 / 框图 / 数据流 / 运行 / 问题记录；视频一镜到底。

原则：先画图，后搭环，再添砖；先能跑，后能稳，最后补文档。

常见翻车点清单

翻车点表现怎么避免
抄 AI 代码不验证能跑，被问一行就卡壳1.6 的必须动作：diff 逐行审 → 编译 → 实机验证
Git 一次提交全部历史只有「first commit: 全部完成」小步提交，完成一个功能就 commit 一次
只调通一次就交演示时重启一次就翻车连续运行 5 分钟 + 反复断电重启测试
不会描述问题只喊「电机不转」按提问模板带齐现象 / 期望 / 已尝试 / 数据
只调参数不理解参数说不清 Kp 变大为何震荡每次改参数记下现象，回看 1.5 概念
拖到最后三天节奏崩掉，只能抄按 D1~D14 建议节奏走，D14 是缓冲日
交付物不齐缺 README / 缺视频把交付物清单当 checklist 逐项打勾

最危险的不是代码写错，而是「能跑」掩盖了「不懂」——答疑与验收时都会追问到讲不清为止。

答疑提问模板：四要素 + 一猜测

现象

描述你看到了什么，而不是你的结论（写「电机不转」，别写「电机坏了」）。

期望

你希望发生什么，尽量量化。

已尝试

你做过哪些排查、结果如何——证明动过脑子，也避免别人重复。

数据 / 截图

日志、报错原文、照片。一张截图胜过一百个字。

【现象】电机上电后不转，串口无输出（具体、可复现）
【期望】上电后能以 1000 RPM 恒速旋转
【已尝试】1. 检查 CAN 线序（通过） 2. 换电机（依旧不转）
          3. 加打印：CAN 初始化返回错误码 0x03
【数据】串口日志截图 + 接线照片 + 报错原文
【猜测】怀疑 CAN 波特率配置不匹配

提问前先自查三步：先看报错原文 → 先查资料 → 先复现一次。还解决不了再按模板提问。
