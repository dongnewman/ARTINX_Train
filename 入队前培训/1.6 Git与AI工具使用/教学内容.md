# 1.6 Git 与 AI 工具使用

> 本节目录 / 建议课时：90 分钟（讲课 45 + 实操 45）｜前置要求：1.5（已经能独立写程序、调电机、看报错）

经过 1.1~1.5，你已经能独立完成「写代码 → 编译 → 烧录 → 调车」的完整流程。但一个人的代码库是脆弱的：

- 昨天车还跑得好好的，今天改了两个小时，电机开始抽风，你想回到昨天——只能靠记忆和 Ctrl+Z；
- 队友改了 CAN 驱动，你完全不知道他动了哪里；
- 比赛前代码突然崩了，想回滚到上周的稳定版本，却发现根本没留备份。

这一节给你的开发装上两件装备：

1. **Git**：给代码「存档」，任何时刻都能回到过去任意一个状态；
2. **AI 工具**：一个 24 小时在线的「副驾驶」，帮你读代码、查资料、定位问题。

## 学习目标

- [ ] 用自己的话说出 Git 是什么、解决了什么问题
- [ ] 独立完成 `init → add → commit → push / pull` 最小工作流
- [ ] 会建分支、合并分支，遇到冲突能按步骤处理
- [ ] 按「小步提交 + 规范提交信息」约束自己
- [ ] 知道三类主流 AI 编程工具及各自适用场景
- [ ] 按「正确姿势」使用 AI：先自己读代码 → 让 AI 解释 → 改完必查 git diff → 编译 → 实机验证
- [ ] 能复述本节总纲：**AI 用于辅助开发，不代替开发者对系统的理解和判断。**

## 核心概念

### 概念一：Git 是什么——你的代码「游戏存档」

玩塞尔达、原神这类游戏时，打 Boss 之前你会先存档：赢了继续，输了读档重来，想试一条新路线就开个新存档。

写代码完全一样，而且更需要存档：

- 调 PID 调到整车发抖，想回退到昨天那个「跑得稳稳的版本」；
- 想大胆试一个激进方案，又怕把好代码改坏；
- 想知道「我/队友到底改了什么、什么时候改的、为什么改」。

**Git 就是给代码拍快照的工具**。它是版本控制系统（Version Control System，VCS）：每当你完成一小块工作，就手动存一个「存档点」，之后随时可以查看、对比、回到任意一个存档点。

> 一句话总结：**Git 是给代码拍快照的工具，任何时刻都能回到拍过的任意一张快照。**

它解决三个问题：

| 你的烦恼 | Git 的答案 |
|---|---|
| 改坏了想回退 | 回到任意一个旧存档 |
| 不知道改了什么 | 每个存档都记录了改动和说明 |
| 多人改同一个项目 | 每人一个「平行世界」，最后合并 |

### 概念二：仓库、提交与「三区」

**仓库（Repository）** 就是「存档文件夹」——一个被 Git 管理的项目目录。执行 `git init` 后，普通文件夹里多出一个隐藏的 `.git` 文件夹，你所有的存档点都存在里面。

**提交（Commit）** 就是「存档点」。每 commit 一次，Git 就给整个项目拍一张快照，并记录四件事：**谁**、**什么时候**、**改了什么**、**为什么改**（写在提交信息里）。每个 commit 有一个唯一编号（一串十六进制的哈希值，如 `3fa2c1b`），就像存档的编号，靠它就能随时「读档」。

为什么要「add 再 commit」两步？Git 把一次提交分成了三个区：

```
工作区（你正在编辑的文件）
   │  git add（挑好想存档的改动）
   ▼
暂存区（购物车：准备存档的内容）
   │  git commit（结账，拍快照）
   ▼
版本库（.git 里的一串存档点）
```

- **工作区（Working Directory）**：你正在改的文件，改完还没存档；
- **暂存区（Staging Area）**：像超市购物车，你可以挑挑拣拣，把一部分改动放进来；
- **版本库**：已经存好的所有存档点。

分两步的好处：一次 commit 可以只装**一个主题**的改动（比如只提交「修了 CAN 超时」，不夹带顺手改的 PID 参数），以后回看历史一目了然。

一个 commit 长什么样？用 `git log` 查看（不加参数时每个存档显示四要素）：

```
commit 3fa2c1b7a9c0e4d...        ← 存档编号（哈希值）
Author: 你的名字 <你的邮箱>       ← 谁
Date:   Wed Aug 12 21:30:00 2026 ← 什么时候

    fix: 修复 CAN 超时重发        ← 为什么（提交信息）
```

> 一句话总结：**commit 是带说明的存档点，add 是挑选要存档的内容放进购物车。**

### 概念三：分支——平行世界

**分支（Branch）** 就是游戏的「平行世界」。你的主线存档叫 `main`；开一个新分支，等于把当前主线复制一份，在新的平行世界里随便折腾，主线毫发无损。

为什么需要分支？两个典型场景：

1. **大胆试验**：想试试「把 PID 参数调激进一点会不会更猛」——开个分支去试，改炸了直接把分支删掉，main 完好如初；改好了就合并（merge）回主线。
2. **多人协作**：你和队友各自在自己的分支上开发，互不干扰，做完各自合并。

```
main:   C1 ── C2 ── C3 ────── M1（合并，同时包含两条线的成果）
                          /
exp:                      E1（只在平行世界里存在的试验）
```

注意两点：在 exp 分支上提交，**main 的代码完全不变**；合并之后，exp 分支本身还在（想删可以删），只是它的成果进入了 main。

> 一句话总结：**分支让你「练级不污染主线」，改炸了删分支，改好了合并。**

### 概念四：远程仓库与 clone / pull / push

**远程仓库（Remote Repository）** 就是「云存档服务器」——放在 GitHub / Gitee / 战队内部 Git 平台上的仓库副本。它解决三件事：换电脑不丢代码、硬盘坏了有备份、多人协作有共同的中转站。

托管平台怎么选：**个人学习**用 GitHub（全球最大代码托管平台，开源项目多）或 Gitee（国内访问快）；**战队项目**用哪个平台、账号怎么申请，按战队统一安排（讲解时演示，不要自己乱建战队相关仓库）。平台只是「放云存档的地方」，Git 命令完全一样，学会一个平台其他都通用。

三个动词：

| 命令 | 游戏类比 | 含义 |
|---|---|---|
| `git clone 地址` | 拷贝别人的存档 | 把云端仓库（含全部历史存档）完整下载到本地 |
| `git push` | 上传云存档 | 把本地新的存档点上传到云端 |
| `git pull` | 下载云存档 | 把云端新的存档点下载并合并到本地（pull = 下载 + 合并） |

本地和云端是**两份完整独立的存档**，push / pull 让它们保持同步。任何一边坏了，另一边都还在。

> 一句话总结：**push 是上传云存档，pull 是下载云存档，clone 是第一次整盘拷贝。**

### 概念五：最小可用工作流与「后悔药」

这是你今后 90% 时间在用的流程。每一步都附「这步发生了什么」和「怎么撤销这一步」。

第一次使用先设置存档署名（只需要做一次）：

```bash
git config --global user.name  "你的名字"
git config --global user.email "你的邮箱"
```

| 步骤 | 命令 | 发生了什么 | 后悔药（撤销这一步） |
|---|---|---|---|
| 1 | `git init` | 当前文件夹变成仓库，生成隐藏的 `.git` | 删掉 `.git` 文件夹，退回普通文件夹 |
| 2 | `git add .` | 所有改动进入暂存区（购物车） | `git restore --staged .`（放回货架，改动还在） |
| 3 | `git commit -m "说明"` | 拍下一张带说明的快照 | 还没 push：`git reset HEAD~1`（撤销存档，改动回到工作区） |
| 4 | `git remote add origin 你的仓库地址` | 绑定云存档地址（只需一次） | `git remote remove origin` |
| 5 | `git push -u origin main` | 本地上传到云端 | 已 push 的不要删，用 `git revert 编号` 生成一条「反向存档」 |
| 6 | `git pull` | 云端下载并合并到本地 | 拉取前先 commit 或 `git stash`；出冲突按概念六处理 |

三个「查看系」命令，无事也要常看：

```bash
git status            # 现在在哪个分支、购物车里有什么、哪些文件改过
git log --oneline --graph   # 存档点列表 + 分支图
git diff              # 本次改动和上次存档相比，具体差在哪
```

`git status` 的典型输出怎么看（这是你每天看最多的画面）：

```
On branch main
Changes to be committed:          ← 暂存区（购物车）：已经 add，还没 commit
        new file:   Core/Inc/motor.h

Changes not staged for commit:    ← 工作区：改了，但还没 add
        modified:   Core/Src/motor.c
```

养成习惯：**每次 commit 之前，先 `git status` 确认购物车里装的是什么。**

**`.gitignore` 一句话**：把编译产物写进去（如 Keil 的 `Objects/`、`Listings/`、`*.o`、`*.uvguix`），这样 `git add .` 就不会把它们放进购物车——编译产物能随时重新生成，体积大且每个人机器上不一样，**不要提交**。

关于撤销，再补两个安全提示：

- 上表的后悔药全部**只影响本地**（remote add 除外）；云端存档一旦 push，就当作「已经发给队友了」，不要用强制手段改写云端历史。
- 你可能见过 `git reset --hard`——它会把工作区改动**直接抹掉**，找不回来。**新手阶段禁止使用**，想「回到某个旧版本」时用 `git switch`/`git checkout 编号` 查看，或开新分支处理，改动先 `git stash` 保底。

> 一句话总结：**init 建仓库，add 挑内容，commit 存快照，push/pull 同步云存档，每一步都有后悔药。**

### 概念六：团队协作规范

团队开发的铁律五条：

1. **小步提交**：一次 commit 只做一件事。好处：出问题好定位、好单独回滚。坏例子：攒了三天改动一个 commit 全交了，标题只能写「更新」。
2. **提交信息写清楚，动词开头**：统一格式 `类型: 简述`，类型常用 `feat`（新功能）、`fix`（修 bug）、`docs`（文档）、`refactor`（重构）。好例子：`fix: 修复云台 pitch 在 -90° 附近抖动`；坏例子：`更新`、`111`、`asdf`。
3. **push 之前先 pull**：先把队友的新存档拉下来合并，再上传自己的，避免 push 被拒。
4. **不直接 push 到 main**：main 是「稳定主线」，任何改动都开分支做，做完通过合并（团队里常走 Pull Request 让队友审查）进入 main。
5. **冲突了别慌，先看 diff**：合并冲突（conflict）不是灾难，只是两个分支改了同一处，Git 不敢替你决定。打开文件，会看到标记：

```
<<<<<<< HEAD
target = 3000;   // 你改的
=======
target = 4000;   // 队友改的
>>>>>>> exp
```

和队友商量保留哪个版本（或合并两者），删掉 `<<<<<<<`、`=======`、`>>>>>>>` 三行标记，再 add + commit 即可。

两条补充：

1. **未提交的改动「跟着人走」**：切换分支时，没 commit 的改动会带到新分支去。所以切分支前要么提交、要么 `git stash`（把改动临时收起来）。反过来这也可以救命——在 main 上改了半天才发现应该在分支上？直接 `git switch -c 新分支`，改动会原封不动跟你过去。
2. **团队常走 PR（Pull Request，拉取请求）流程**：在自己的分支上做完 → 在网页上发起 PR → 队友在网页上审查你的 diff、提意见 → 通过后合并进 main。本质就是「分支 + 合并 + 人工审查」。

> 一句话总结：**小步提交、信息规范、先 pull 后 push、分支进 main、冲突看 diff。**

### 概念七：AI 编程工具有哪些

工具更新换代很快，但类型就三类，按「介入程度」从深到浅：

| 类型 | 代表 | 适合干什么 |
|---|---|---|
| 对话式 Coding Agent | Claude Code、Cursor 等 | 能读整个工程、按指令修改多个文件；适合「帮我在工程里加一个功能」 |
| IDE 插件 | VS Code 的 Copilot、Cline 等 | 写代码时实时补全、选中一段代码让 AI 解释或改写；适合小块辅助 |
| 网页版对话 | DeepSeek、Kimi、ChatGPT 等 | 查资料、解释概念、报错排查、写小段独立代码 |

选型建议：入门先用**网页版**查资料和解释报错；熟悉后把**IDE 插件**装进 VS Code；需要让 AI 干「跨文件大活」时再用 **Coding Agent**。注意合规：使用哪家工具、账号怎么申请，按战队统一安排走（训练时演示）。

使用前想清楚三件事：

1. 这个工具**更新换代很快**，上面的名字过几个月就可能变化，学的是「类型」而不是某个具体产品；
2. **不要复制粘贴自己看不懂的代码**——每条代码都要能讲出它在干什么；
3. 涉及账号、付费、学生认证等，以工具官网当时政策和战队安排为准。

> 一句话总结：**网页版查资料，IDE 插件补小块，Agent 干大活——按需选用。**

### 概念八：AI 的正确打开方式

核心原则：**AI 是副驾驶，你是驾驶员**——方向盘和刹车永远在你手里。AI 说对了可以加速，说错了你得能兜住。

五个高频场景的正确姿势：

1. **阅读陌生代码**：把一段没见过的代码（比如战队工程里的某个模块）贴给 AI：「逐段解释这段代码的作用，不要修改」。注意顺序——**先自己读一遍再问**，带着问题问，学得比直接要答案快得多。
2. **查询资料**：问「STM32 CAN 波特率怎么算、常见坑有哪些」，比「帮我写好全部代码」更有价值。
3. **解释报错**：把**完整报错信息 + 相关代码 + 你已经试过的办法**一起贴给 AI，问可能原因和排查顺序。信息给得越全，答案越靠谱。
4. **辅助定位问题**：描述现象（如「电机上电后不转，CAN 灯正常」），让 AI 列出可能原因清单，你**逐项亲自验证**。
5. **辅助修改代码**：给出明确需求 + 约束：「在 set_speed 函数里加速度限幅，保持现有代码风格，不要动其他部分」。

正确姿势全流程（七步）：

```
① 先自己读一遍代码（至少知道它在干什么）
② 向 AI 描述问题和上下文（贴代码、贴报错）
③ 让 AI 先解释、给方案，而不是直接改
④ 确认方案后，再让它动手改
⑤ git diff 逐行看它改了什么
⑥ 编译通过（0 error 0 warning）
⑦ 实机验证（先空转/低速，再正常工况）
   不通过 → 带着新现象回到 ②
```

提问质量决定回答质量，附「五个场景的提问模板」（直接套用）：

```
① 解释代码：
「逐段解释这段代码的作用，只解释、不要修改：
（贴代码）」

② 解释报错：
「这段代码编译报错如下，我已经试过 XX。请按可能性从高到低
列出原因，并给出每条的排查步骤：
（贴完整报错 + 相关代码）」

③ 定位问题：
「现象：电机上电不转，CAN 灯正常，我怀疑是 XX。
请列出 5 个可能原因，按可能性排序，并说明我该怎么逐项验证。」

④ 修改代码：
「在 set_speed 函数里加速度限幅 ±5000，保持现有代码风格，
不要改动其他部分。改完告诉我你改了什么、为什么。」

⑤ 追问与求证：
「你刚才说最可能的原因是 XX，依据是什么？我自己怎么验证？」
```

三个常见误区，请对号入座：

1. **让 AI 重写整个文件**：改动面越大越难审，还容易丢掉你原来写好的细节。要求「最小改动」永远是第一约束。
2. **不追问直接采纳**：AI 说「可能是 XX」，你不验证就照着改。AI 也会错，错的结论会把你带进沟里。
3. **查完资料不验证**：AI 说「这个寄存器的第 3 位是 XX」，你抄进代码才发现手册写的不是这样。**涉及硬件的结论，一律回官方手册/数据手册核对。**

> 一句话总结：**先自己读、让 AI 解释、再让它改，改完必查 diff、必编译、必实机验证。**

### 概念九：检查 AI 的修改——它可能一本正经地写 bug

AI 写的代码**看起来都很对**，这是它最危险的地方。常见 bug 类型：

- 条件写反（`>` 写成 `<`）；
- 单位搞错（弧度 vs 角度、ms vs s）；
- 边界漏掉（数组越界、除零）；
- 顺手「优化」了不该动的地方（比如删掉一个错误处理分支）。

**反例（小明）**：让 AI 给云台 pitch 加速度限幅，AI 改完他看都没看直接编译烧录上车。结果一上电云台疯转——回头 `git diff` 一看，AI 把 `if (target > MAX)` 写成了 `if (target < MAX)`，限幅变成了「放大」。烧录前只要多看一眼 diff，就不会发生。

**正例（小红）**：让 AI 改 CAN 发送函数后，先 `git diff` 逐行看改动，发现 AI 顺手删掉了一个错误处理分支，当场让 AI 加回来；编译通过后先空转观察、再低速上车验证，一切正常才 commit。

AI 改完后的「必须动作清单」：

1. `git diff` 逐行读改动——**看不明白的改动，一律问 AI 或删掉**；
2. 编译通过（0 error）；
3. 实机验证：先空载/低速，再正常工况；
4. 全部没问题，才 commit。

> 一句话总结：**AI 写的代码看起来都对，所以必须 diff 逐行审、编译、实机验——三个都过才算数。**

### 概念十：总纲——辅助开发，不代替判断

AI 不坐你的车、不站你的赛场、不承担你代码的责任。代码出了事，定位问题、修复、复验的人是你；AI 给出的每一个结论，最终签字验收的都是你。因此本节最重要的一句话：

> **AI 用于辅助开发，不代替开发者对系统的理解和判断。**

## 动手实践

### 任务一：给 PID 工程建存档（本地 Git 入门）

**前提**：拿出 1.5 节你的电机 PID 工程目录（复制一份用来练手）。

0. 确认 Git 已安装：执行 `git --version`，应输出类似 `git version 2.4x.x`。
   - 自查点 ✔：若提示「不是内部或外部命令」，回 1.1 重装 Git 并勾选 Add to PATH，然后重开终端。
1. 在工程目录打开终端（VS Code 里 Ctrl+`），执行 `git init`。
   - 预期现象：提示 `Initialized empty Git repository`。
   - 自查点 ✔：`ls -a` 能看到 `.git` 文件夹。
2. 新建文件 `.gitignore`，写入（Keil 工程常用）：

```bash
# .gitignore —— 编译产物不入库
Objects/
Listings/
*.o
*.d
*.uvguix*
*.uvoptx
```

3. 执行 `git status`，观察哪些文件「未跟踪」；执行 `git add .`，再 `git status`，看文件状态变绿（进入暂存区）。
   - 自查点 ✔：`.gitignore` 里的目录没有出现在待提交列表里。
4. 执行 `git commit -m "init: 提交 1.5 PID 工程基础版本"`。
5. 改一行代码（比如把目标速度 3000 改成 4000），先 `git diff` 看改动内容，再 `git commit -m "feat: 目标速度调整为 4000"`。
   - 自查点 ✔：`git log --oneline` 看到两条存档。
6. 练习「后悔药」：`git reset HEAD~1` 撤销最后一次 commit。
   - 预期现象：改动回到工作区（`git status` 显示文件已修改未暂存），`git log` 少了一条。
7. 玩分支：

```bash
git branch exp-speed          # 开平行世界
git switch exp-speed          # 进入平行世界
# 把 PID 参数改激进一点，然后：
git commit -m "exp: 激进 PID 参数"
git switch main               # 回到主线，发现代码恢复原样
git merge exp-speed           # 把平行世界的成果合并回主线
```

   - 自查点 ✔：切回 main 后代码是旧参数；merge 后 main 里出现新参数。
8. 故意制造一次冲突，练手解决流程：

```bash
git switch -c conflict-demo      # 开分支，把目标速度改成 3000 并 commit
git switch main                  # 回主线，把同一行改成 5000 并 commit
git merge conflict-demo          # 预期现象：提示 CONFLICT，自动合并失败
```

   - 预期现象：打开冲突文件，看到 `<<<<<<<` / `=======` / `>>>>>>>` 三行标记。
   - 做法：保留你想要的版本（比如 5000），删掉三行标记，`git add .` + `git commit`。
   - 自查点 ✔：`git log --oneline --graph` 能看到两条线合成一条。

### 任务二：云存档（远程仓库）

1. 注册 GitHub 账号（国内访问慢属正常现象；使用哪个平台按战队统一安排，训练时演示）。
2. 在网页上新建一个空仓库（**不勾选** Add a README），复制仓库地址。
3. 绑定并上传：

```bash
git remote add origin 你的仓库地址
git push -u origin main
```

   - 自查点 ✔：刷新网页，能看到提交历史和文件列表。
4. 在另一个目录 `git clone 你的仓库地址`，得到一份完整拷贝（连历史存档都在）。
   - 自查点 ✔：`git log` 在两个目录里内容一致。
5. 在 A 目录改东西 → commit → push；在 B 目录 `git pull`。
   - 预期现象：B 目录的代码和存档都被更新。
6. 拓展（选做）：在 GitHub 上新建一个分支，网页上直接编辑 README 并提交，再在本地 `git pull`，观察云端提交如何进入本地。
   - 自查点 ✔：`git log` 里能看到那条在网页上做的提交。
7. 学生认证福利（选做）：GitHub 学生包可解锁 Copilot 等工具，申请条件与权益以官网当时政策为准。

### 任务三：AI 辅助调试实战

1. 在工程里故意制造一个 bug（例如把速度输出除以 2，或还原一个你之前遇到的报错），编译烧录，**先自己**读报错/看现象，写下你的假设。
2. 把「完整报错 + 相关代码 + 你的假设」贴给 AI，让它解释原因并给出排查顺序。参考提问模板（概念八）：

```
现象：电机转速只有设定值的一半。
我改过的地方：（贴 git diff 输出）
我的假设：可能是我把编码器读数乘了 2。
请按可能性排序给出原因和排查步骤。
```

3. 按 AI 给的顺序逐项排查，记录哪一步真正定位到问题——对比一下 AI 的建议和你自己的假设。
4. 让 AI 给出修复方案，**先看方案**，确认合理后再让它改。
5. 执行必须动作清单：`git diff` 逐行审 → 编译 → 实机验证。
6. 把修复后的版本 commit，提交信息写清楚：`fix: 修复转速减半（编码器换算系数错误）`。
7. 写一段 100 字小结：这次 AI 的哪些帮助有效、哪些无效。

参考：AI 容易写出的一类 bug（限幅条件写反）：

```c
/* 错误版本：条件写反，限幅变成了"放大" */
void set_target_speed(int16_t target)
{
    if (target < MAX_SPEED) {   /* bug：应为 target > MAX_SPEED */
        target = MAX_SPEED;
    }
    motor_target = target;
}

/* 正确版本 */
void set_target_speed(int16_t target)
{
    if (target > MAX_SPEED) {
        target = MAX_SPEED;
    }
    motor_target = target;
}
```

### 任务四（选做）：双人协作模拟

## 常见问题与排查

| 现象 | 可能原因 | 排查方法 |
|---|---|---|
| `git` 不是内部或外部命令 | 安装时没勾选 Add to PATH，或装完没重开终端 | 参考 1.1 重装 Git 并勾选 Add to PATH；重开终端；`git --version` 确认 |
| push 被拒绝（non-fast-forward） | 云端有本地没有的新提交 | 先 `git pull` 再 `git push`；有冲突按冲突流程处理 |
| 合并冲突，文件里出现 `<<<<<<<` | 两个分支改了同一处代码 | 打开文件，和队友商量保留哪个版本，删掉三行标记，add + commit |
| commit 完才发现改错了 | 提交前没看 `git diff` | 没 push：`git reset HEAD~1`；已 push：`git revert 编号` 生成反向提交 |
| 不小心把编译产物提交了 | 没写 `.gitignore` | `git rm -r --cached Objects` 移出跟踪，补写 `.gitignore` 后再提交 |
| 终端里中文文件名乱码 | 编码设置问题 | `git config --global core.quotepath false`；文件统一存成 UTF-8 |
| AI 给的代码编译一堆错 | 直接照抄、没带上下文 | 把完整报错和相关代码贴回给 AI；更重要的是自己读懂每一行 |
| AI 的解释头头是道、实测却不对 | AI 不了解你的工程细节，可能一本正经地胡说 | 对重要结论自己查证或实测；只把 AI 当助手，判断在自己 |
| 在 main 上改了代码才发现该在分支上做 | 忘记先建分支 | 未提交的改动会跟着人走：`git switch -c 新分支名`，改动自动带到新分支，再 commit |
| 切换分支时提示会覆盖本地改动 | 未提交改动与目标分支冲突 | 先 commit 或 `git stash`（临时收起改动）再切，之后 `git stash pop` 取回 |
| AI 给的方案看着合理但不敢直接改 | 对改动后果没把握 | 先在 `git switch -c 试验分支` 上让 AI 改，验证通过再合并回主线——Git 就是你的安全网 |

## 课后自测

1. 为什么 `git add` 和 `git commit` 要分成两步？
2. 在 exp 分支上提交之后，main 分支的代码会变吗？merge 之后呢？merge 完 exp 分支还存在吗？
3. push 被拒绝（non-fast-forward）最常见的处理流程是什么？
4. 团队为什么不允许直接 push 到 main？
5. 列出 AI 改完代码后的「必须动作清单」（至少 4 步）。
6. 「AI 写的代码能编译、能跑，就是对的」这句话错在哪里？
7. 在 main 分支上改了 10 分钟代码，才想起来应该在一个新分支上做，怎么办？

<details>
<summary>参考答案</summary>

1. add 是「挑选要存档的内容」放进暂存区，commit 才真正存成存档点；分两步可以保证一次提交只包含一个主题的改动，历史更清晰、更好回滚。
2. 不会变——分支是平行世界；merge 后 exp 的改动进入 main；exp 分支本身依然存在，确认没用了可以 `git branch -d exp` 删掉。
3. 先 `git pull` 把云端新提交拉下来合并；若出现冲突，打开文件、商量保留哪个版本、删掉冲突标记，再 add + commit + push。
4. main 是稳定主线，直接 push 容易把未验证、有冲突的代码带进主线；分支开发 + 合并（或 Pull Request）让每一步都可审查、可回滚。
5. ① `git diff` 逐行审查改动；② 编译通过（0 error）；③ 实机验证（先空载/低速再正常工况）；④ 确认无误才 commit。
6. 能跑不等于符合需求、更不等于没有边界 bug——AI 不了解你的整车上下文，可能写出条件写反、单位搞错、漏边界之类的逻辑错误，必须 diff 审查 + 实测把关。
7. 不用慌：未提交的改动会跟着人走，直接 `git switch -c 新分支名`，改动原封不动带到新分支，再 commit 即可。

</details>

## 本节速查卡

Git 命令速查（日常 90% 就这几条）：

| 想干什么 | 命令 |
|---|---|
| 看现在什么状态 | `git status` |
| 看存档列表 + 分支图 | `git log --oneline --graph` |
| 看这次改了什么 | `git diff` |
| 全部放进购物车 | `git add .` |
| 存一个存档点 | `git commit -m "类型: 简述"` |
| 开平行世界并进去 | `git switch -c 分支名` |
| 回到主线 | `git switch main` |
| 合并分支到当前分支 | `git merge 分支名` |
| 上传云存档 | `git push` |
| 下载云存档 | `git pull` |
| 后悔 add | `git restore --staged .` |
| 后悔 commit（没 push） | `git reset HEAD~1` |
| 临时收起改动 | `git stash` / 取回 `git stash pop` |

AI 使用姿势速记：

| 场景 | 一句话口诀 |
|---|---|
| 读代码 | 先自己读一遍，再让 AI 解释 |
| 查资料 | 问「怎么算、坑在哪」，不直接要成品 |
| 报错 | 完整报错 + 代码 + 已试过的办法 |
| 定位问题 | AI 列清单，你逐项验证 |
| 改代码 | 明确需求 + 约束，先看方案再让改 |
| 改完 | diff 逐行看 → 编译 → 实机验证 → 才 commit |
