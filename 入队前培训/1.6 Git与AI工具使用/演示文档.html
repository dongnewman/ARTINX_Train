Git 是什么：版本控制系统

定义

Git 是分布式版本控制系统（Version Control System，VCS）：对项目文件持续记录快照（commit），支持查看、对比、回退到任意历史版本。

类比一句话：给代码做「存档」，随时读档。

开发痛点Git 的答案
改坏了想回退回到任意一个旧提交
不知道改了什么每次提交记录改动与说明
多人改同一项目各自分支开发，最后合并

四个核心概念

概念定义一句话类比
仓库 Repository被 Git 管理的项目目录，历史快照存于 .git存档文件夹
提交 Commit项目的一次快照，记录谁 / 何时 / 改了什么 / 为什么存档点
分支 Branch从主线分出的独立开发线，互不影响，可合并平行世界
克隆 clone把远程仓库（含全部历史）完整拷贝到本地拷贝别人的存档

一次提交经过三个区

工作区（正在编辑的文件）
   │  git add     挑选改动
   ▼
暂存区（购物车：待提交内容）
   │  git commit  拍快照
   ▼
版本库（.git 中的提交历史）
  • 工作区：正在改的文件，未存档
  • 暂存区：add 挑选的内容，一次提交一个主题
  • 版本库：commit 生成的快照序列
.gitignore：把编译产物（Objects/、Listings/、*.o、*.uvguix）写入，add 时自动忽略。

最小可用工作流

步骤命令作用后悔药（撤销）
1git init当前目录变为仓库删除 .git 目录
2git add .改动加入暂存区git restore --staged .
3git commit -m "说明"生成一条快照git reset HEAD~1（未 push）
4git remote add origin 地址绑定远程仓库（一次）git remote remove origin
5git push -u origin main上传到远程git revert 编号（不删历史）
6git pull下载并合并远程更新拉前先 commit / stash
已 push 的提交视为已发布，禁止强制改写远程历史；git reset --hard 会抹掉工作区改动，新手禁用。

三个查看命令与状态解读

git status
      当前分支 / 改动状态
git log --oneline --graph
      提交历史与分支图
git diff
      与上次提交的逐行差异

习惯：commit 前先 git status 确认暂存区内容。

分支 Branch：独立开发线

main:  C1 ─ C2 ─ C3 ── M1（合并）
                      /
exp:                  E1（试验改动）

exp 上提交不影响 main；merge 后改动进入 main，exp 分支本身仍在。

  • 在分支上试验激进方案，改坏即删
  • 多人各自分支开发，互不干扰
  • 切换分支时未提交改动会跟随
  • main 保持稳定可运行，验证后合并

团队协作规范五条

  1. 小步提交：一次 commit 只做一件事，好定位、好回滚
  2. 提交信息动词开头：fix: 修复云台 pitch 抖动（feat / fix / docs / refactor）
  3. push 之前先 pull：先合并队友更新，避免 push 被拒
  4. 不直接 push 到 main：分支开发 + 合并，团队走 Pull Request 审查
  5. 冲突先看 diff：两个分支改了同一处，商量后解决再提交

合并冲突：别慌，先看 diff

<<<<<<< HEAD
target = 3000;   // 你改的
=======
target = 4000;   // 队友改的
>>>>>>> exp

冲突 = 两个分支改了同一处，Git 不替你决定，只标记位置。

  • 与队友商量保留哪个版本
  • 删除 <<<<<<< / ======= / >>>>>>> 三行标记
  • add + commit 完成合并

AI 工具：副驾驶

AI 辅助开发，不代替开发者对系统的理解和判断

AI 编程工具三类

类型代表适用场景
对话式 Coding AgentClaude Code / Cursor读整个工程，跨文件改功能
IDE 插件GitHub Copilot / Cline补全、选中解释、小块改写
网页版对话DeepSeek / Kimi / ChatGPT查资料、解释报错、写小段代码
选型：入门先用网页版，再装 IDE 插件，跨文件大活用 Agent；工具迭代快，学类型不背产品名。

AI 正确姿势七步

  1. 先自己读一遍代码
  2. 带上下文向 AI 描述问题
  3. 让 AI 先解释、给方案
  4. 确认方案后再让它改
  5. git diff 逐行看改动
  6. 编译 0 error
  7. 实机验证，不通过回到 2
三个误区：让 AI 重写整个文件；不追问直接采纳；查完资料不核对硬件手册。
AI 是副驾驶，你是驾驶员：方向盘和刹车在自己手里。

提问模板（直接套用）

「逐段解释这段代码，只解释、不要修改」+ 贴代码

「编译报错如下，我已试过 XX。按可能性列出原因
  和排查步骤」+ 贴完整报错 + 相关代码

「现象：电机上电不转，CAN 灯正常。列 5 个可能
  原因，按可能性排序，说明怎么逐项验证」

「在 set_speed 里加 ±5000 速度限幅，保持现有
  风格，最小改动。改完说明改了什么、为什么」

「你刚说原因是 XX，依据是什么？我怎么自己验证？」

AI 改完必须做的四步

必须动作清单

  1. git diff 逐行审查，看不懂就问或删
  2. 编译 0 error
  3. 实机验证：先空载低速，再正常工况
  4. 确认后才 commit

典型 bug 与正反例

AI 常见问题：条件写反、单位搞错、边界漏掉、顺手删掉错误处理分支。

反例：不看 diff 直接烧录，if (target < MAX) 把限幅写成放大；正例：diff 发现被删的保护分支，要求加回，验证后才提交。

判断：AI 改对了吗？

案例一：AI 加的两行限幅

if (t > 5000)  t = 5000;
if (t < -5000) t = -5000;

 

案例二：AI 改完的另一个版本

if (t < 5000)  t = 5000;
if (t > -5000) t = -5000;

 

常见问题与排查

现象原因与处理
git 不是内部或外部命令重装并勾选 Add to PATH，重开终端
push 被拒（non-fast-forward）先 git pull 再 push
合并冲突出现 <<<<<<<保留正确版本、删标记、add + commit
commit 完才发现改错了未 push 用 reset HEAD~1；已 push 用 revert
误提交编译产物写 .gitignore，再 git rm -r --cached 目录
在 main 上改了才发现该开分支git switch -c 新分支，改动跟随
AI 给的代码编译一堆错带完整报错追问；自己读懂每一行
AI 方案看着合理但不敢改开试验分支验证，通过再合并
