# 2.8 整车调车

> 本节目录 / 建议课时：180 分钟（讲课 40 + 实车 140，建议与校内赛备赛同步进行）｜前置要求：2.1–2.7
>
> 本节目标：在上一代完整车辆上，按 10 步规范顺序完成一轮完整调车，建立「分模块调试、逐步集成、问题记录、回归验证」的调车习惯。

## 核心概念

### 概念一：调车的第一性原理——一次只调一个变量

**先给结论：一次只动一个旋钮。同时动三个旋钮，现象变了，你也不知道是谁干的。**

调车和做实验是同一件事：改变输入，观察输出。如果你同时改了电机方向、PID 参数和代码分支，然后车「变好了」——哪个改动起的作用？不知道。更糟的是：其中两个改动其实有害，只是被第三个改动的效果盖住了。等到第三个改动在别的工况下失效，两个「地雷」一起爆炸。

什么叫「一个变量」：

| 例子 | 是「一个变量」吗 |
|---|---|
| 把左前轮的 Kp 从 0.8 改成 1.0 | ✅ 是，一个参数的一处改动 |
| 把四个轮子的 Kp 全改一遍 | ❌ 四个变量一起动 |
| 换了一根线，顺便改了代码 | ❌ 两个变量 |
| 改了参数，但没记下来改了什么 | ❌ 等于两个变量：参数 + 你的记忆 |

「变量」不只是参数——线束、电池、遥控映射、代码分支、机械限位，全都是变量。**判断标准只有一个：它会不会影响现象。会影响的，就一次只动它一个。**

配套纪律：

1. **动手前，先记录现状**（参数值、现象），保证随时能改回去。
2. **动一个，观察，记录结果**。没效果就改回去，再动下一个。
3. **不要「顺手」**。「顺手把另一个参数也调了」是调车现场最危险的动作。

> **一句话总结：一次只调一个变量，是调车界的「控制变量法」——没记录、没对比的改动等于赌博。**

### 概念二：从最底层往上调——电气没查完不动软件

**先给结论：调车像盖楼，一层一层往上盖。下层没验收，上层盖得越漂亮塌得越彻底。**

整辆车是一摞「层」，每一层都踩在下面一层的肩膀上：

```
第 9~10 层  视觉联调、整车功能      ← 最上层
第 7~8 层   底盘整体、云台底盘联动   ← 系统级
第 4~6 层   云台、底盘单轮（闭环）   ← 模块级
第 3 层     电机方向、编码器反馈      ← 反馈级
第 2 层     遥控器与输入             ← 输入级
第 1 层     电气：供电、线束、CAN     ← 地基
```

逐层说说「为什么它在下面」：

- **第 1 层（电气）**：供电不稳、线束虚接、CAN 掉线时，你在第 6 层看到的任何现象（转速不对、电机不转、偶尔抽风）都**没有分析价值**——它们可能全部来自地基问题。而且电气问题往往是「间歇性」的：接头虚接的典型表现就是「跑着跑着突然掉线」，这种问题不在一开始排除，后面会伪装成任何其他层的 bug。
- **第 2 层（输入）**：遥控数值都不对，你调 PID 时看到的「响应不对」可能只是「指令不对」。先确认你发的指令长什么样，再讨论车对指令的执行。
- **第 3 层（方向与反馈）**：方向反了、反馈符号反了，你调出来的 PID 参数全是「为错误系统调的」。等把方向改对，参数全部作废，白调一下午。更危险的是反馈反了会变成**正反馈**——车自己把自己越推越快。
- 从第 4 层开始才是「调控制参数」的世界。前面三层花的时间，是后面每一层调参都能加速的「投资」。

所以有了两句口诀：

- **电气没查完不动软件**——线、电、CAN 先验完。
- **方向没对完不调 PID**——开环方向、反馈符号先验完。

> **一句话总结：从最底层往上调，每一层都必须是「已知正确」的，上层结论才有意义。**

### 概念三：顺序本身就是排查策略——第 3 步错了，第 7 步没法定位

**先给结论：10 步顺序不是仪式，是排查算法。跳步省下的时间，会在定位问题时加倍还回来。**

假设你跳过第 3 步（方向检查），直接调第 7 步（底盘整体运动），现象是「底盘乱窜、原地打转」。请回答：是哪个轮子的问题？

- 可能左前轮方向反了；
- 可能右后轮编码器反馈反了（速度环变成正反馈，一个轮满速疯转）；
- 可能运动学解算里某个符号错了；
- 可能四个轮子里有两个都有问题，负负得正，看起来像另一个问题。

四种可能叠加在一起，你只能把四个轮子、反馈、代码全查一遍——这就是「从头排查」，第 3 步一点没省下来，还多浪费了第 7 步的时间。

反过来，如果第 1~6 步都通过了，第 7 步出问题，排查范围就被锁死在**第 7 步新引入的东西**里（整车运动解算、四轮配合），十分钟就能定位。

一个完整的「跳步 vs 按顺序」对比：

```
跳步调车：  第 7 步出问题 → 嫌疑范围 = 全部 10 步 → 排查一下午
按顺序调：  第 7 步出问题 → 嫌疑范围 = 第 7 步新增部分 → 排查十分钟
```

10 步之间的依赖关系：

```
① 电气检查 ─→ ② 遥控输入 ─→ ③ 方向与反馈 ─┬─→ ④ 云台 Pitch ─→ ⑤ 云台 Yaw
                                            │
                                            └─→ ⑥ 底盘单轮 ─→ ⑦ 底盘整体 ─→ ⑧ 云台底盘联动 ─→ ⑨ 视觉联调 ─→ ⑩ 整车功能
```

> **一句话总结：每通过一步，就排除一层嫌疑。顺序就是「二分法」——只不过是把排查做在了出问题之前。**

### 概念四：分模块调试 + 逐步集成——一次只引入一个新模块

**先给结论：先让每个零件单独转起来，再让它们碰面。碰面时一次只来一个新朋友。**

- **分模块调试**：云台 Pitch 先单独调（④），底盘单轮先单独调（⑥）。每个模块独立达到通过标准，才允许进入「集成」。
- **逐步集成**：集成时一次只引入一个新模块。云台 Pitch 过了才加 Yaw（⑤）；底盘四轮都过了才合成整车（⑦）；云台、底盘各自稳定了才做联动（⑧）；电控这边稳了才接视觉（⑨）。
- 为什么不能「一步到位」：两个不稳定的模块集成在一起，现象是「两个问题的卷积」——你看到的震动，既可能来自 A 也可能来自 B 也可能来自 A 和 B 的相互作用。**模块越多，现象越不可读。**
- 为什么「单轮速度环先于整车运动」（第 6 步在第 7 步前面）：整车运动 = 运动学解算 + 四个速度环。如果速度环本身没调好，整车跑偏时你分不清是「解算错了」还是「环没跟上」。单轮先闭环，等于把「每个轮子听不听话」的问题先解决掉，整车只负责「四个轮子怎么配合」。
- 生活类比：拼乐高。每拼上一块，先晃一晃确认稳了，再拼下一块。等到成品倒了才发现中间有块松的，就得全拆。

> **一句话总结：单模块闭环先跑通，再逐步集成；每次集成只引入一个「新朋友」，出问题就知道找谁。**

### 概念五：问题记录——没记录的问题等于没修过

**先给结论：调车是长跑（跨天、跨人、跨车），你的大脑不可靠，日志才可靠。**

调车现场最贵的两个问题是：「上次是谁动了参数？」和「这车昨晚还好好的」。这两个问题，一个有日志就秒答，没有日志就查一下午。

日志模板（7 个字段，先背下来）：

| 字段 | 填什么 | 反例 |
|---|---|---|
| **日期** | 当天日期（跨天调车才有时序） | 不填，两天后分不清先后 |
| **车辆** | 哪辆车、哪台车架 | 「那辆车」 |
| **步骤** | 对应 10 步中的哪一步 | 不填，不知道现象属于哪一层 |
| **现象** | 客观事实：「前进时车身向右偏」 | 「车坏了」 |
| **数据** | 读数、截图、曲线、参数值 | 「转速有点低」 |
| **改动** | 从几改成几：「右前轮 Kp 0.8→1.0」 | 「调了下参数」 |
| **结果** | 改完现象如何、要不要回归 | 不填，等于白改 |

空白模板可以直接抄：

```markdown
## 调车日志
| 日期 | 车辆 | 步骤 | 现象 | 数据 | 改动 | 结果 |
|---|---|---|---|---|---|---|
|      |      |      |      |      |      |      |
```

一条填好的示例（后面演示文档里也有交互版）：

```markdown
| 日期 | 车辆 | 步骤 | 现象 | 数据 | 改动 | 结果 |
|---|---|---|---|---|---|---|
| 2026-08-12 | 上一代步兵车 | 第 7 步 | 前进时车身持续向右偏 | 右前轮 950 RPM（目标 1000） | 右前轮 Kp 0.8→1.0 | 右偏减小，待回归第 6 步 |
```

三条纪律：

1. **现象写客观事实**，不写形容词。形容词（「有点抖」）无法复现，数据可以。
2. **改动必须可回滚**。写「从几到几」，回不去也要知道改了什么。
3. **当场记**。收工再补的日志，和凭记忆写的 bug 报告一样不可信。

> **一句话总结：调车日志是给「明天的你」和「你的队友」写的——没记录的问题等于没修过。**

### 概念六：回归验证——防止「修好一个、弄坏三个」

**先给结论：系统是耦（ǒu）合的。修 A 可能弄坏 B，所以修完必须回头把 B 再验一遍。**

耦合的意思是：改一个地方，别的地方会跟着变。典型场景：

- 把底盘电机限幅改小（保护电机）→ 整车加速变慢，第 7 步「走直线」的通过标准不再满足；
- 改了云台 Yaw 参数 → 第 8 步联动时云台开始抖；
- 换了电源线/电池 → 第 1 步的电气状态、各模块的供电余量全变了。

**回归验证**就是：修完一个问题，回头把「之前已经通过」的步骤重跑一遍。做法：

1. 维护一张**回归清单**：每次调车，把当天已经通过的步骤打勾。
2. 修完任何一个问题后，把回归清单从头勾一遍（至少勾到当前步骤）。
3. 回归通过才叫「修完了」；回归挂了，先记录，再处理——顺序不乱。

回归清单长这样（例子）：

```markdown
## 回归清单（当天已通过）
- [x] ① 电气检查（上电无掉线）
- [x] ② 遥控输入（通道数值正常）
- [x] ③ 方向与反馈（四轮一致）
- [x] ④ 云台 Pitch（阶跃稳定）
- [x] ⑤ 云台 Yaw（指向稳定）
- [x] ⑥ 底盘单轮（速度环跟随）
- [ ] ⑦ 底盘整体（走直线）   ← 当前步骤
```

回归验证和「一次只调一个变量」是配套的：变量单一，回归才快。你只改了一个参数，回归时就不用重新怀疑其他东西。

一个真实的节奏演示（假想的半天调车）：

```
14:00  第 7 步通过（走直线 ✔）
14:30  发现新问题：急加速时右偏 → 改右前轮 Kp 0.8→1.0
14:40  现象好转，但——回归第 6 步：右前轮单轮阶跃出现轻微震荡
14:50  记录：Kp 1.0 单轮震荡，回退到 0.9
15:00  回归通过：第 6、7 步全部复验 ✔ → 日志闭环
```

看到没有：改一个参数，回头重跑第 6 步，问题在 10 分钟内被拦住。没有回归的话，「轻微震荡」会潜伏到晚上整车测试才爆发。

> **一句话总结：修完一个 bug，回头跑一遍回归清单——防止「修好一个、弄坏三个」，也防止「修完就忘了自己改过哪里」。**

### 概念七：安全红线——先保人，再保车

**先给结论：调车现场的第一优先级永远是人，然后是车，最后才是进度。以下五条是红线，不是建议。**

1. **车轮架空或车辆垫起**：调车时底盘必须离地（用调车架/垫块架空），或整车用支架垫起。一辆全速的步兵车撞上脚踝，不是开玩笑的。麦轮车贴地调，随时可能「贴地起飞」。
2. **遥控急停随时可触发**：急停拨杆/按键永远在手指边上，主调手离急停不超过一次反应。上车前先试急停，确认有效再继续。
3. **旁边有人看护**：调车至少两人在场——安全员负责盯电源、线束、车辆状态和周围的人。单兵作战不调车。
4. **电池充电安全**：充电有人看护；不过充；鼓包、破损、发烫的电池立即停止使用并单独存放。锂电池起火不是「概率问题」，是「有没有预案」的问题。
5. **上电顺序**：**先开遥控器（发射端），再给车上电；断电时先断车电，再关遥控器。** 原因：遥控器先开，信号先存在，车一上电就处于「被控」状态；断电反过来，车在失去信号前先失去动力，不会「失联乱跑」。

五条红线的共同点：**它们都不是「技术上做不到」，而是「图省事就不做」**。调车现场出事，从来不是因为车有多快，而是因为有人觉得「就这一次，没事」。

> **一句话总结：架空、急停、看护、电池、上电顺序——五条红线，任何一条被破坏，立刻停下来处理。**

## 动手实践：10 步调车 SOP

### 10 步 × 前置知识对照表

本节不教新知识，它把 2.1–2.7 学过的所有东西排成一条流水线。调到哪一步卡住，就先回去翻对应的小节：

| 步骤 | 主要用到哪节的知识 |
|---|---|
| ① 电气与设备检查 | 2.6 整车电气（供电、线束、CAN） |
| ② 遥控与输入 | 2.2 裁判系统 + 2.6（遥控接收链路） |
| ③ 方向与反馈 | 1.4 电机与基础控制（编码器、CAN 指令） |
| ④ ⑤ 云台 Pitch / Yaw | 2.5 PID 与前馈（位置闭环） |
| ⑥ 底盘单轮 | 1.5 + 2.5（速度环） |
| ⑦ 底盘整体 | 2.4 运动学（麦轮解算） |
| ⑧ 云台—底盘联动 | 2.4 + 2.5（坐标变换、串级） |
| ⑨ 视觉联调 | 2.2（串口协议）+ 2.7（抓包工具） |
| ⑩ 整车功能 | 2.1 规则研读（功能需求清单） |
| 全流程的记录与排查 | 2.7 调试与问题定位（分层定位、工具） |

---

> 本节使用**上一代完整车辆**进行实车训练。具体参数（CAN 连接、电调型号、遥控映射、代码接口）以车队现场车辆为准（讲解时结合战队现有代码展示）。
>
> 三人一组分工：**主调**（拿遥控/键盘，只负责操作）、**记录员**（拿调车日志，只负责记录）、**安全员**（拿电源，只负责安全）。角色可以轮换，但同一时刻一人只干一件事。

### 第 0 步：准备与分工（约 15 分钟）

1. **清点工具**：内六角、万用表、串口线、CAN 工具（如有）、调车日志模板（纸质或电子）、垫车架。
2. **确认车辆状态**：电池电量、上次日志的遗留问题（如果上次没写日志，先把这次的分工讲清楚）。
3. **试急停**：上电前先空跑一遍「遥控急停 → 车辆断电」的路径，确认有效。
4. **确认分工**：主调、记录员、安全员各就各位。
5. ✔ 自查：三个人都知道自己干什么；日志模板已打开，第一条已写下日期和车辆。

### 第 1 步：整车电气与设备检查（约 20 分钟）

- **检查什么**：线束（磨损、松脱）、接头锁紧、主控与各模块供电、CAN 总线连通、电池电压。
- **怎么看**：断电时肉眼检查 + 用手轻拉关键接头（虚接的接头一拉就露馅）；上电后看各模块指示灯、读电池电压与各模块在线状态（讲解时结合战队现有代码/工具展示）。
- **通过标准**：上电后所有模块指示灯正常、CAN 无掉线、电池电压在安全范围、轻拉线束无复位。
- **常见坑**：接头「看着插上了」其实没锁紧（上电时通、跑起来断）；上届留下的线束老化；电池鼓包仍在用。
- **预期现象**：这一步是「全绿」检查，任何一盏灯不对、任何一个模块不在线，都停在这里，不进下一步。
- ✔ 自查：万用表量过关键供电点并记录数值。

### 第 2 步：遥控器与输入检查（约 15 分钟）

- **检查什么**：遥控器与接收机对频、每个拨杆/拨轮的通道映射、死区、摇杆行程对应的数值范围。
- **怎么看**：通过上位机或串口打印遥控数据（讲解时结合战队现有代码展示），逐个通道拨动，观察数值变化方向和范围。
- **通过标准**：每个通道数值稳定、变化方向与直觉一致、松开回中、行程覆盖预期范围。
- **常见坑**：通道映射错（摇杆控制到了别的轴）；数值方向反了；死区没设导致回中后仍有输出。
- **预期现象**：拨杆推到「前进」位置，打印出来的对应通道值增大且为正——和直觉一致。
- ✔ 自查：在日志里记录每个通道的「最小值 / 中值 / 最大值」。

### 第 3 步：电机方向和反馈检查（约 30 分钟）

- **检查什么**：每个电机「给正指令时朝什么方向转」+「编码器读数方向是否与期望一致」。
- **怎么看**：给单个电机一个小的正电流（开环），观察转向；同时读编码器，正向转动时读数应增加（按车队约定，讲解时以现有代码为准）。
- **通过标准**：四个底盘电机「同样指令 → 相对车体同样的运动方向」；反馈符号与运动方向一致（正向运动 → 读数增加）。
- **常见坑**：某个电机方向装反（线序反 / 电调设置反）；编码器符号反（速度环会变成正反馈：给目标后满速疯转）；空转方向对、装上轮子反了。
- **预期现象**：同一指令下，四个轮子朝车体的同一方向转（相对车体），而不是「左前顺时针、右前逆时针」这种不对称。
- ✔ 自查：四轮逐一测试并记录，不跳测、不抽查。

参考代码（方向与反馈检查，开环给电流）：

```c
/* 第 3 步用：开环给单个电机一个小电流，检查方向 */
void Step3_CheckOneMotor(int can_id)
{
    int16_t test_current = 1000;        /* 小电流，单位以电调协议为准 */
    Motor_SetCurrent(can_id, test_current);   /* 1.4 学的：发控制量 */

    /* 边看转向，边打印编码器读数 */
    for (int i = 0; i < 100; i++) {
        uint16_t enc = Encoder_GetCount(can_id);   /* 1.4 学的：读反馈 */
        printf("enc = %u\r\n", enc);
        HAL_Delay(20);
    }

    Motor_SetCurrent(can_id, 0);        /* 测完立刻停 */
    /* 判断：轮子朝期望方向转？读数在增加（按约定）？
       两项都符合才给这个电机打勾。 */
}
```

### 第 4 步：云台 Pitch（约 30 分钟）

- **检查什么**：Pitch 轴电机方向、反馈、机械零位、限位；然后才是位置闭环。
- **怎么看**：先做第 3 步的「方向+反馈」检查（对 Pitch 电机同样适用）；再给一个小目标角度，观察响应。
- **通过标准**：小角度阶跃稳定到位、无震荡；限位保护生效（到达限位能停住，不硬顶）。
- **常见坑**：方向没对就先调 PID（参数白调）；限位没接或逻辑反了（云台打到底硬顶、电机过热）；重心偏导致低段扭矩不足。
- **预期现象**：给「抬头 10 度」，云台平滑抬到 10 度附近停住；用手轻压，它能把角度顶回来。
- ✔ 自查：方向 → 反馈 → 零位 → 限位 → PID，五件事按这个顺序逐个确认。

### 第 5 步：云台 Yaw（约 30 分钟）

- **检查什么**：Yaw 轴电机的方向与反馈；如果 Yaw 使用 IMU 反馈，检查 IMU 安装方向与坐标轴映射。
- **怎么看**：手动转动云台，读 Yaw 角度，确认角度数值与实际转动方向一致；再给目标角度观察闭环响应。
- **通过标准**：Yaw 指向稳定、无持续漂移（或漂移在可接受范围内）、阶跃无震荡。
- **常见坑**：IMU 坐标轴映射错（转了 90° 它以为转了 -90°）；Yaw 与底盘联动时的补偿方向反（留到第 8 步查）。
- **预期现象**：给「右转 30 度」，云台平滑右转到 30 度停住；手拧云台，它自己转回去。
- ✔ 自查：手动转云台 → 读角度 → 方向一致，记录在日志。

### 第 6 步：底盘单轮（约 40 分钟）

- **检查什么**：单轮速度环——给目标速度，看实际速度跟随（2.5 的 PID 知识在这里上场）。
- **怎么看**：一次只控一个轮子，串口打印目标/实际速度（或用 2.7 学的工具画曲线）。
- **通过标准**：阶跃响应跟得上、无持续震荡、稳态误差小（标准以车队现有车为准，讲解时演示）。
- **常见坑**：跳过单轮直接调整车（四个轮子的问题混在一起）；反馈方向反导致正反馈（给目标后该轮满速）；单轮测试时其他轮子没断电被拖着转。
- **预期现象**：给目标 1000 RPM，实际速度快速跟上并在目标附近稳定；改目标到 2000 再回 0，响应不震荡。
- ✔ 自查：四个轮子每个都单独跑过速度环并留下曲线/数据。

参考代码（单轮速度环阶跃测试）：

```c
/* 第 6 步用：单轮速度环阶跃，观察跟随 */
void Step6_SingleWheelStep(int can_id)
{
    int16_t target = 1000;              /* 目标转速，按实际车辆取安全值 */
    for (int i = 0; i < 1000; i++) {
        if (i == 500) target = 2000;    /* 阶跃：500ms 后改目标 */
        float current = Encoder_GetSpeedRPM(can_id);      /* 1.4 学的 */
        float out = PID_Calc(&speed_pid, target, current, 0.001f); /* 1.5 学的 */
        Motor_SetCurrent(can_id, (int16_t)out);
        if (i % 10 == 0) printf("tgt=%d cur=%.1f\r\n", target, current);
        HAL_Delay(1);
    }
    Motor_SetCurrent(can_id, 0);
}
```

### 第 7 步：底盘整体运动（约 40 分钟）

- **检查什么**：四轮合体——前进 / 横移 / 旋转是否按运动学解算正确执行（2.4 的知识）、车身是否跑偏。
- **怎么看**：低目标速度起步，分别只发「前进」「横移」「旋转」三种指令，观察车身轨迹。
- **通过标准**：前进走直线、横移不歪、原地旋转不漂移（低速下肉眼可判）。
- **常见坑**：某轮方向反（现象：车身打转、横移变成旋转——回到第 3 步查）；轮距/运动学参数与实车不符；机械装配导致轮子不垂直、胎压/磨损不一致。
- **预期现象**：只发「前进」，车身笔直向前；只发「横移」，车身横向平移不旋转；只发「旋转」，车身原地自转不漂走。
- **故障走查示例（重点）**：现象「前进变成原地打转」。因为第 3、6 步已通过，先排除单轮方向和单轮速度环问题；查运动学解算：把四个轮的指令值打印出来，看是否四个轮「同号同幅」（前进时应四轮同速同向）。若解算值正确而车仍打转，回到第 3 步核对「哪个轮子相对车体的方向装反」。
- ✔ 自查：出问题先回第 3、6 步确认单轮状态，不直接改整车参数。

### 第 8 步：云台—底盘联动（约 30 分钟）

- **检查什么**：底盘旋转/运动时，云台指向是否相对大地保持稳定；云台运动范围与车体有无机械干涉。
- **怎么看**：慢速原地旋转底盘，观察云台是否反向补偿（底盘转，云台反向转、指向不动）；再试前进时云台是否稳定。
- **通过标准**：底盘自旋时云台指向稳定、补偿方向正确；全行程无干涉、无异响。
- **常见坑**：补偿方向反了（底盘转，云台跟着转，转向速度翻倍）；底盘运动导致云台供电波动/重心晃动；机械干涉（云台撞到装甲板/线束被挂住）。
- **预期现象**：底盘慢速自旋一圈，云台始终指向同一个方向（比如一直对着墙上某点）。
- ✔ 自查：先慢速旋转底盘，确认补偿方向正确后再提速。

### 第 9 步：视觉联调（约 60 分钟，与视觉组配合）

- **检查什么**：视觉发来的目标位置/角度能否被云台正确执行；通信链路（串口等）稳定无乱码丢包。
- **怎么看**：视觉组给出目标，观察云台指向；用 2.7 学的工具抓通信数据核对。
- **通过标准**：视觉给目标 → 云台指向目标；连续运行一段时间数据帧无异常。
- **常见坑**：坐标系不统一（视觉的 x/y 与云台的 pitch/yaw 对不上）；单位不统一（弧度 vs 度）；协议字段对错位。**三方先对接口文档，再上机。**
- **预期现象**：视觉给出「目标在左前方 20 度」，云台平滑转过去并停住。
- ✔ 自查：坐标系、单位、协议三项在联调前书面确认。

### 第 10 步：其他整车功能（约 30 分钟）

- **检查什么**：拨弹、发射、装甲/裁判系统状态、模式切换等剩余整车功能，逐项过。
- **怎么看**：每项功能单独触发，观察执行结果与裁判系统反馈。
- **通过标准**：各项功能按需求运行，且互不干扰（如发射时底盘不失控、拨弹时不掉线）。
- **常见坑**：功能之间相互干扰（发射瞬间底盘限流、云台抖动）；「都差不多了」跳过不常用的功能——比赛时就抓瞎。
- **预期现象**：逐项打勾，每项功能按设计工作，且运行中其他模块无异常。
- ✔ 自查：逐项打勾，全部通过才算「这辆车可以交」。

### 收尾：完整日志 + 回归清单归档

每次收工前做三件事：

1. 把当天的日志整理一遍，未闭环的问题（改了没验证的）标红。
2. 更新回归清单，确认今天通过的步骤。
3. 给下一个接手的人写一句话交接（车现在的状态、下一步该做什么）。

### 与校内赛结合（建议节奏）

大纲建议本节与校内赛备赛合并进行。一个可行的安排：

- **第 1 周**：集中完成第 1~6 步，把这辆车「打地基」打牢。校内赛的第一场考核往往就是「底盘能不能稳定地按指令走」。
- **第 2 周**：完成第 7~10 步，进入「能打」状态；视觉联调与校内赛的视觉组进度对齐。
- **赛前每次训练**：上车后先按回归清单快速过一遍当天用到的步骤（约 10 分钟），再开始针对性训练。
- **赛后**：把比赛/训练中暴露的问题记入日志，定出下一次调车的目标——**带着问题清单来调车，而不是来了现找问题**。

校内赛最大的价值不是赢，是让你在「有压力、有时间限制」的场景里，把这套调车纪律变成肌肉记忆。

### 数据怎么记（回顾 2.7 的工具）

调车日志里的「数据」一栏，常见来源：

| 数据 | 工具 | 适用场景 |

## 常见问题与排查

| 现象 | 可能原因 | 排查方法 |
|---|---|---|
| 上电后电机不转 | 供电 / CAN 掉线 / 线束虚接 | 回到第 1 步逐项查；再回到单电机开环测试 |
| 跑着跑着突然掉线/复位 | 接头虚接（振动时断开） | 第 1 步：轻拉线束观察是否复位 |
| 给目标速度后电机满速疯转 | 编码器反馈方向反（正反馈） | 第 3 步：核对反馈符号与转向 |
| 底盘前进变成原地打转 | 某个轮子方向反 / 运动学映射错 | 回第 3 步四轮逐一核对；再查解算符号 |
| 底盘横移变成旋转 | 运动学解算符号错 / 轮距参数错 | 检查解算系数；回第 7 步低速单指令验证 |
| 底盘低速走不直 | 轮胎磨损/气压不一、轮子不垂直 | 机械检查；四轮速度环数据对比 |
| 云台到位后不停震荡 | PID 参数过大 / 反馈噪声 / 机械虚位 | 减小增益；查反馈数据；查机械固定 |
| 云台打到底不停、电机发烫 | 限位没接 / 限位逻辑反 | 第 4 步：限位保护单独验证 |
| 底盘旋转时云台跟着转 | 联动补偿方向反了 | 第 8 步：补偿符号取反再试 |
| 视觉目标总打偏一个固定角度 | 坐标系 / 单位 / 协议不一致 | 第 9 步：三方对接口文档 |
| 「这车昨晚还好好的」 | 有人动过参数 / 线束松动 / 电池老化 | 查日志；查接头；查电池内阻 |
| 修好一个问题后别的功能坏了 | 系统耦合，改动了共享部分 | 按回归清单从头勾一遍 |

## 课后自测

1. 用自己的话说说「一次只调一个变量」和「从最底层往上调」各是什么意思，各举一个调车现场的反例。
2. 为什么第 3 步（电机方向）做错了，第 7 步（底盘整体运动）出问题时「没法定位」？反过来，如果 1~6 步都通过了，第 7 步出问题应该先查什么？
3. 调车日志的 7 个字段分别是什么？「现象」一栏写「车坏了」为什么不合格？
4. 什么叫回归验证？举一个「修好一个、弄坏三个」的耦合例子（可以是你在车上遇到过的）。
5. 背出 5 条安全红线。为什么断电时要「先断车电、再关遥控器」？
6. 云台 Pitch 出现「到位后不停震荡」，按 10 步顺序，你的排查路径是什么？列出前三个检查项。
7. 「底盘前进变成原地打转」，如果第 3、6 步都已通过，你的排查顺序是什么？
8. 第 6 步（底盘单轮）为什么要放在第 7 步（底盘整体）前面？少做第 6 步会有什么后果？

<details>
<summary>参考答案（先自己想，再看答案）</summary>

1. 「一次只调一个变量」：每次只改一个参数/一处代码/一根线，改完观察记录，便于归因；反例：同时把四个轮子的 Kp 都改了。「从最底层往上调」：电气、输入、反馈先验完才动控制算法；反例：线束虚接时调 PID 调一下午。
2. 因为方向、反馈、控制量全都未经验证，第 7 步的异常可能是任意一层问题的叠加，只能全部重查。反之若 1~6 步都通过，问题几乎必然在第 7 步新引入的部分（整车解算、四轮配合），先查解算符号和轮距参数。
3. 日期、车辆、步骤、现象、数据、改动、结果。「车坏了」是结论不是现象，无法复现、无法归因；应写客观事实如「前进时车身向右偏」。
4. 回归验证 = 修完一个问题后，把之前通过的步骤（回归清单）重跑一遍。耦合例子：底盘限幅改小 → 整车加速变慢，第 7 步「走直线」通过标准不再满足（举例不限，言之成理即可）。
5. 架空/垫起、急停随时可触发、有人看护、电池充电安全、上电顺序。断电先断车电再关遥控器，是为了让车先失去动力而不是先失去信号——避免「车还有电但已经没有控制信号」的危险窗口。
6. 按顺序回查：第 3 步核对 Pitch 电机的反馈方向与符号；第 4 步核对零位与限位；再查 PID 增益是否过大（先减 P）。方向、反馈、限位都排除了才动参数。
7. 第 3、6 步已过 → 嫌疑锁定在第 7 步新增部分：先打印四个轮子的解算指令，确认「前进」时四轮指令同号同幅；若指令正确，再回第 3 步核对是否某个轮子相对车体装反（第 3 步测的是电机出轴方向，装车后还可能错）。
8. 整车运动 = 运动学解算 + 四个速度环。速度环没调好时，整车跑偏分不清是「解算错」还是「环没跟上」。少做第 6 步的后果：第 7 步出问题时四个轮子的环状态未知，只能退回第 6 步重查——跳步省的时间加倍还回来。
</details>

## 延伸资源（自学用）

1. **RoboMaster 2025 机甲大师高校系列赛比赛规范文件**（RoboMaster 官网）——《比赛规则手册》《参赛手册》《机器人制作规范手册》官方下载页。调车的「通过标准」很多直接来自机器人制作规范手册（供电、尺寸、功率限制等），调车前先把最新版翻一遍。  
   https://www.robomaster.com/zh-CN/resource/pages/announcement/1768
2. **RoboMaster 官方社区 · 规则/资料中心**（bbs.robomaster.com）—— 规则手册、技术评审、培训体系等官方资料的导航总入口，找不到某份文件时从这里进。  
   https://bbs.robomaster.com/wiki/20204847
3. **【rm工程】寒假调车寄录～**（B 站，2.3 万播放）—— 一位 RM 工程机器人电控队员的寒假调车记录。看真实调车现场的节奏：改一点、试一下、记录、再改。  
   https://www.bilibili.com/video/BV1wP4y167Qk
4. **华南理工大学机器人实验室《RM2021 舵轮步兵电控开源》**（GitHub，Apache-2.0）—— 华南虎 2021 赛季舵轮步兵整车电控，按「云台板 / 底盘板 / CAN 板 / 舵机板」分工程组织。看看强队把一辆整车拆成哪些模块、怎么分工，正好对照本节 10 步顺序。  
   https://github.com/scutrobotlab/RM2010_AGVinfantry
5. **湖南大学跃鹿战队 basic_framework**（GitHub，300+ star）—— RM 电控通用框架：bsp / module / app 三层，底盘、云台、发射等模块以 pub-sub 消息解耦。学完本节可以对照框架，理解「模块化」在真实工程里的样子。  
   https://github.com/HNUYueLuRM/basic_framework
6. **华中科技大学狼牙战队 HUST_HeroAim_2024**（GitHub，RM2024 开源奖优秀奖）—— 英雄机器人辅瞄开源（视觉侧）。README 里写得很实在：他们靠「场上观测日志」发现官方前哨站转速存在约 5% 误差——这就是「数据记录」在定位问题时的实战价值。  
   https://github.com/HUSTLYRM/HUST_HeroAim_2024

- [ ] 能背出 10 步调车顺序和每步的通过标准
- [ ] 能解释「电气没查完不动软件、方向没对完不调 PID」

- [ ] 在实车上完成了第 7~10 步（整车、联动、视觉、功能）并留下日志

- [ ] 能随时背出 5 条安全红线，并在调车现场遵守
