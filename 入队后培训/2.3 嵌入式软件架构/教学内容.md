# 2.3 嵌入式软件架构

> 本节目录 / 建议课时：120 分钟（讲课 60 + 实操 60）｜前置要求：1.7 入队综合作业（写过单文件裸机程序）

你已经能让一个电机转起来、写出一个能跑的 PID 闭环。但当你打开战队的整车工程时，看到的会是几十个文件夹、上百个文件、层层调用的函数——和你在单文件里写的 `while(1)` 完全不是一回事。

这一节回答两个问题：

1. **一个功能应该放在哪里**（分层：BSP / Device / Module / Application）
2. **不同模块之间如何配合**（接口、数据流、状态机、控制周期、RTOS 任务）

学完这一节，你应该能：看着战队的工程目录，说出每一层在干什么；跟着一份数据（比如电机转速）从硬件一路走到控制器；并且能自己写出一个带状态机的周期控制任务。

## 核心概念

### 概念一：为什么要分层——用「公司」来理解软件架构

先回忆一个痛点：你在入队前写的程序，是**单文件裸机程序**——一个 `main.c` 里塞进初始化、CAN 收发、PID、按键扫描，再加一个巨大的 `while(1)`。几百行的时候还行；几千行的时候，改一个电机方向可能要翻遍整个文件，三个人一起写代码天天打架（改同一个文件）。

机器人不是「一个程序」，而是几十个功能同时工作：云台要跟手、底盘要平移、摩擦轮要稳速、裁判系统要上报、遥控器要解析……如果全堆在一起，代码会变成一锅粥。

**解决办法就是分层（Layering）：像公司一样，把代码按职责分成部门和上下级。**

| 层 | 公司类比 | 职责 | 举例 |
|---|---|---|---|
| Application（应用层） | 总经理 | 调度全局：遥控输入、裁判数据、启动各模块 | 「裁判系统说比赛开始，通知云台进入跟随模式」 |
| Module（模块层） | 业务部门 | 管一个完整功能：状态机、控制器（PID）、业务逻辑 | 云台模块、底盘模块、功率控制模块 |
| Device（设备层） | 设备管理员 | 管一个具体外设：收发协议帧、解析数据、维护设备状态 | 电机设备（收发电调 CAN 帧）、IMU 设备 |
| BSP / Driver（板级驱动层） | 物业 | 管硬件寄存器：时钟、引脚、外设初始化、底层收发 | HAL 库、CAN 初始化、UART 收发一个字节 |
| 硬件（Hardware） | 大楼本身 | 芯片、总线、电机、传感器 | STM32、CAN 总线、3508 电机 |

**调用规则（重点，背下来）：**

1. **只能向下调用**：总经理找业务部门，业务部门找设备管理员，设备管理员找物业。反过来不行——物业不可能指挥总经理。
2. **不能跳级太多**：Application 一般通过 Module 做事，不直接戳寄存器。
3. **同层尽量不互相调用**：云台模块和底盘模块之间要协作，走 Application 中转或消息队列，而不是互相调函数。
4. **唯一合法的「向上」是回调（Callback）**：下层注册一个函数给上层，事件发生时被调用（比如 CAN 中断来了，调 Device 层注册好的解析函数）。

> **一句话总结：分层 = 按职责拆部门 + 只能向下调用。它让每个文件只解决一个问题，让多人协作不再打架。**

```
         Application（总经理：调度全局）
              │ 调用
              ▼
         Module（业务部门：状态机 + 控制器）
              │ 调用
              ▼
         Device（设备管理员：协议解析 + 设备状态）
              │ 调用
              ▼
         BSP（物业：寄存器 + 外设初始化）
              │ 读写
              ▼
         硬件（STM32 / CAN / 电机）
```

**这套架构长什么样？** 打开一个分层良好的工程，你通常会看到（讲解时对照战队工程确认实际命名）：

| 文件夹/文件形态 | 属于哪层 | 内容特征 |
|---|---|---|
| `bsp/`、`driver/`、`hal/` 之类 | BSP | 全是初始化函数，不含业务名词 |
| `device_xxx.c/h` 或含设备名的 struct | Device | 协议帧解析、设备状态字段 |
| `module_xxx.c/h`、`gimbal/`、`chassis/` | Module | 状态机、PID、业务逻辑 |
| `main.c`、`tasks.c`、`app/` | Application | 任务创建、全局调度 |

**为什么这能解决协作冲突？** 因为「谁负责哪个文件」和「谁负责哪件事」对上了：调云台 PID 的人改 Module 层文件，换电机型号的人改 Device 层文件，两个人几乎不会改到同一个文件——这正是公司分工的价值。

> **对照战队框架的实际目录**（讲解时打开 `_frame/` 工程逐项对照）：
> - **BSP 层** → `bsp/`：其中 `board/` 是手写驱动（`bsp_can`、`bsp_led` 等），`cubemx/` 是 CubeMX 生成的初始化；这一层是 C 语言。
> - **Device 层** → `components/` 里的设备组件：`CanMotor`（`CanMotorManager` + DJI/`DjiCanMotorCommander` + MIT 电机）、`Rc`（遥控器 DR16）、`Imu`、`Referee`（裁判系统）等，都是 C++ 类。
> - **Module 层** → `components/Controller/RoboController`（状态机 `State_Relax` / `State_HandleInput`）+ `algorithm/Pid`（控制器用的 PID）。
> - **跨层通信** → `message/`：`MessageManager` 的发布/订阅，正是本文「同层尽量不互相调用」那条规则的落地点。
> - **Application 层** → `components/Controller/ControllerTask.cpp`（RTOS 任务入口，`osDelay(1)` 即 1kHz 控制周期）。
> 注意：框架上层（`components` / `algorithm` / `message`）是 C++（`.hpp`/`.cpp` + 类），只有 `bsp/` 是 C。

### 概念二：五层逐个看——每一层「能调用谁、被谁调用」

**BSP / Driver（板级支持包，Board Support Package）**

- 它是什么：离硬件最近的一层，把「写寄存器」翻译成人话。比如「把 PA0 拉高」变成 `HAL_GPIO_WritePin(...)`；「初始化 CAN，波特率 1Mbps」变成一个初始化函数。
- 被谁调用：被 Device 层调用。
- 能调用谁：只调用硬件本身（寄存器），不调用任何上层。
- 判断标准：这层里**不应该出现任何机器人业务**。如果你在 BSP 里看到了「云台」「底盘」字样，那一定是放错地方了。

**Device（设备层）**

- 它是什么：管理**一个具体外设**的完整生命周期。比如「电机设备」：它知道 3508 电调的反馈帧格式（哪个字节是转速、哪个字节是角度），负责发控制帧、收反馈帧、解析成「转速是多少 RPM、角度是多少度」这种业务层能直接用的数据。
- 被谁调用：被 Module 层调用。
- 能调用谁：BSP 层。
- 典型接口（一个设备 = 一个 struct + 一组函数）：

```c
/* 电机设备：对外只暴露“数据 + 操作”，隐藏协议细节 */
typedef struct {
    float speed_rpm;      /* 当前转速（已解析好，单位 RPM） */
    float angle_deg;      /* 当前转子角度（度） */
    float current_a;      /* 当前电流（安培） */
    float temp_c;         /* 温度（摄氏度） */
    uint32_t last_feed_ms;/* 最近一次收到反馈的时间戳 */
} Motor_Device_t;

void Motor_Device_Init(Motor_Device_t *dev, uint8_t can_id);   /* 初始化 */
void Motor_Device_SendSpeed(Motor_Device_t *dev, int16_t speed);/* 发送转速指令 */
void Motor_Device_ParseFeedback(Motor_Device_t *dev, uint8_t *data8); /* 解析反馈帧 */
```

**Module（模块层）**

- 它是什么：一个**完整功能**的家。云台模块 = 「云台状态机 + 云台控制器（PID）+ 云台数据」，它用 Device 层拿到的数据做决策，算出一个控制量，再交回 Device 层发出去。
- 被谁调用：被 Application 层调用（通常是「每个周期跑一次」）。
- 能调用谁：Device 层。
- 它里面最重要的两样东西：**状态机**（概念五）和**控制器**（2.5 节会深入）。

**Application（应用层）**

- 它是什么：整车的大脑，负责「谁在什么时候干什么」。遥控器数据进来后分发给云台/底盘；裁判系统发「比赛开始」，通知各模块切状态；底盘功率超限，通知云台降低输出。
- 被谁调用：基本不被调用，它是顶层（main 函数和 RTOS 任务就住在这里）。
- 能调用谁：Module 层（以及一些公共的 Device，比如遥控器设备）。

**控制器（Controller）住在哪？**

控制器（PID 那一套：目标值 → 误差 → 输出）**属于 Module 层**——它是「业务部门」里的核心技术员，不是单独的一层。云台有云台的控制器，底盘有底盘的控制器，各管各的。

> **一句话总结：BSP 管寄存器、Device 管外设、Module 管功能、Application 管全局；控制器是 Module 里的核心成员。**

### 概念三：模块接口——「改内部不影响外部」

分层之后，层和层之间靠**接口（Interface）**对接。接口就是「别人能看到的东西」：struct 和函数签名。

一个好接口长什么样？

```c
/* 云台模块接口：调用者只需要知道“给目标角、问当前角” */
void  Gimbal_SetTargetYaw(float yaw_deg);   /* 设定 Yaw 轴目标角度 */
float Gimbal_GetCurrentYaw(void);           /* 读取当前 Yaw 轴角度 */
```

调用者不需要知道 Gimbal 内部用的是什么电机、PID 参数是多少、走的是 CAN 还是 PWM。这就是**封装（Encapsulation）**：

- **改内部不影响外部**：明年电机从 3508 换成别的型号，只要 `Gimbal_SetTargetYaw` 的签名不变，所有调用它的代码一行都不用改——变化的只是 Device 层里解析协议的那几十行。
- **接口是「合同」**：函数名、参数、返回值就是合同条款。签约之后，两边各自干活，只要合同不变就互不干扰。
- **新手常见错误**：到处用全局变量（`extern float target_yaw;` 满天飞）。全局变量等于「所有人都能随便改」，出了 bug 根本不知道是谁改的。正确做法是把数据藏进 struct，只暴露操作函数。

> **一句话总结：接口 = struct + 函数签名；把实现藏起来，只暴露「做什么」，不暴露「怎么做」。**

### 概念四：数据流——一次电机转速数据的完整旅程

分层架构不是纸上谈兵，它决定了数据在代码里的流动路径。跟着一份真实数据走一遍：

**场景：云台电机（Yaw 轴）的转速，是怎么从电调一路走到云台控制器的？**

电调通过 CAN 总线周期性地（约 1ms 一次）发回**反馈帧**：CAN ID 为 `0x200 + 电机ID`，8 字节数据里装着转子角度、转速（RPM）、电流、温度（这是 RoboMaster 官方电调的公开协议，1.4 节见过）。

```
① 硬件：电调把反馈帧发到 CAN 总线上，STM32 的 CAN 外设自动接收
        │
        ▼
② 中断：CAN 收到一帧 → 硬件触发 CAN RX 中断 → CPU 停下手里的事
        进入中断服务函数（ISR）
        │
        ▼
③ DMA（可选）：中断里只做最少的事——把数据交给 DMA 搬进内存缓冲区，
        或者直接读 FIFO 存进一个环形缓冲区，然后立刻退出
        │
        ▼
④ Device 层：电机设备模块从缓冲区取出 8 字节，按协议解析：
        speed_rpm = 解码(字节2~3)；angle_deg = 解码(字节0~1)
        更新 Motor_Device_t 里的字段，打上时间戳
        │
        ▼
⑤ Module 层：1ms 控制周期到了，云台控制器从 Motor_Device_t
        读出 speed_rpm 和 angle_deg，代入 PID：
        误差 = 目标角 - 当前角 → 算出输出电流值
        │
        ▼
⑥ 反向旅程：输出值 → 云台模块调用 Motor_Device_SendSpeed()
        → Device 层按协议打包成 CAN 控制帧
        → BSP 层把帧塞进 CAN 邮箱 → 硬件发到总线上 → 电调执行
```

这条链路上有三个关键点：

1. **中断里绝不干重活**。解析、计算全部留给后面的层，中断只负责「把货收进门」（见概念七）。
2. **每层只做自己份内的事**。解析协议的不算 PID，算 PID 的不碰寄存器。
3. **时间戳很重要**。数据可能因为总线堵塞而迟到，模块层要能判断「这包数据是 1ms 前的还是 10ms 前的」，2.9 节讲超时处理时会用到。

用一张表把「每一站谁在干活」钉死：

| 站 | 谁在干 | 干了什么 | 干了多久 |
|---|---|---|---|
| 硬件 | CAN 外设 | 自动收帧进硬件 FIFO | 硬件并行，不占 CPU |
| 中断 | ISR | 把帧搬进软件缓冲区，置标志 | 微秒级 |
| DMA | 搬运工 | 可选：大批量数据后台搬运 | 后台并行 |
| Device | 电机设备模块 | 按协议解析出转速/角度，打时间戳 | 微秒级 |
| Module | 云台控制器 | 读数据 → 误差 → PID → 输出 | 几十微秒 |
| BSP | 发送函数 | 把控制帧塞进 CAN 邮箱 | 微秒级 |

**注意「干了多久」这一列**：整条链路必须在一个控制周期（1ms）内走完，且剩下的时间要留给别的任务——这就是概念六要讲的「时间预算」。

> **一句话总结：数据流 = 中断收进缓冲区 → Device 解析 → Module 计算 → Device 打包 → BSP 发出；每层只做份内事。**

### 概念五：状态、模式、状态机

**状态（State）**：系统「此刻是谁」。一台云台，可能处于「关机」「初始化」「跟随」三种状态之一，同一时刻只能是其中一种。

**模式（Mode）**：用户/上层给系统选的「工作方式」，比如「遥控模式」「自瞄模式」。模式决定目标从哪里来，状态决定系统当前在干什么。新手可以先把两者混着理解，但要记住：**模式是选择，状态是事实**。

**状态机（State Machine）**：把「状态 + 事件 + 转移规则」画成图的工具。规则只有一条——**发生某个事件，状态才发生转移**。比如「初始化」状态下，只有收到「标定完成」这个事件，才能进入「跟随」。

云台三状态状态机（状态转移图）：

```
                ┌──────────────────────────────┐
                │                              │
                ▼                              │
   ┌────────┐ 上电   ┌────────┐ 标定完成  ┌────────┐
   │  关机  │ ─────► │ 初始化 │ ────────► │  跟随  │
   │ (OFF)  │        │ (INIT) │           │(FOLLOW)│
   └────────┘        └────────┘           └────────┘
       ▲                 │ 标定失败           │ 急停
       │                 ▼                   ▼
       │            ┌────────┐           ┌────────┐
       └────────────│  保护  │◄──────────│  保护  │
          断电/急停 │ (PROTECT)          │(PROTECT)│
                    └────────┘           └────────┘
```

（演示文档里有可点击的动画版：按「上电」「标定完成」「急停」按钮看状态转移。）

**为什么状态机这么重要？** 因为机器人的状态是「跳跃」的：比赛开始前要标定、比赛中要跟随、被击中要保护、超功率要限幅。如果不用状态机，这些逻辑会散落成一堆 `if`，互相干扰——「标定到一半裁判喊开始了怎么办？」这种问题，if 瀑布根本回答不了，状态机一张图就回答了：**没收到「标定完成」事件，就永远留在「初始化」**。

C 语言实现骨架（switch 状态机，全队最常用写法）：

```c
/* 状态枚举：给每种状态一个名字 */
typedef enum {
    GIMBAL_OFF = 0,    /* 关机：不输出 */
    GIMBAL_INIT,       /* 初始化：自检 + 标定 */
    GIMBAL_FOLLOW,     /* 跟随：正常控制 */
    GIMBAL_PROTECT,    /* 保护：急停/超限，电机放松 */
} GimbalState_e;

static GimbalState_e state = GIMBAL_OFF;  /* 当前状态（static：只在本文件可见） */

void Gimbal_StateMachine_Update(void)   /* 每个周期调用一次（如 100Hz） */
{
    switch (state) {
    case GIMBAL_OFF:
        if (Gimbal_GetPowerOn()) {       /* 事件：上电 */
            state = GIMBAL_INIT;
        }
        break;

    case GIMBAL_INIT:
        Gimbal_Init_Calibrate();         /* 执行标定动作（内部自己计时） */
        if (Gimbal_Init_CalibDone()) {   /* 事件：标定完成 */
            state = GIMBAL_FOLLOW;
        } else if (Gimbal_GetEmergencyStop()) {  /* 事件：急停 */
            state = GIMBAL_PROTECT;
        }
        break;

    case GIMBAL_FOLLOW:
        Gimbal_Follow_Control();         /* 每个周期做跟随控制（调 PID） */
        if (Gimbal_GetEmergencyStop()) { /* 事件：急停 */
            state = GIMBAL_PROTECT;
        }
        break;

    case GIMBAL_PROTECT:
        Gimbal_Motor_Relax();            /* 电机断电/放松 */
        if (!Gimbal_GetEmergencyStop() && Gimbal_GetPowerOn()) {
            state = GIMBAL_INIT;         /* 事件：急停解除，重新标定 */
        } else if (!Gimbal_GetPowerOn()) {
            state = GIMBAL_OFF;
        }
        break;

    default:
        state = GIMBAL_OFF;              /* 防御：未知状态一律回关机 */
        break;
    }
}
```

看骨架的三个要点：

1. **switch 分状态**：每个 case 里只写「这个状态下，做什么 + 等什么事件」。
2. **转移 = 改 state 变量**：状态转移就是给 `state` 赋新值，下一次进来走新的 case。
3. **default 保底**：状态变量可能被意外改写（内存踩踏），default 兜底回安全状态。

> **一句话总结：状态机 = 用「状态 + 事件 → 新状态」的一张图管住所有跳变逻辑；switch 状态机是它的最简实现。**

### 概念六：控制周期——为什么控制环要「掐表」跑

**控制周期（Control Period）**：控制器每隔固定时间执行一次，这个间隔就是控制周期。战队云台/底盘常用的周期是 **1kHz（1 毫秒一次）**，即 1 秒执行 1000 次控制。

**为什么必须固定周期？** 回忆 1.5 节的 PID 公式：

```
输出 = Kp × 误差 + Ki × 误差积分 + Kd × 误差微分
```

积分项里乘的是 `dt`（两次控制之间的时间），微分项里除的是 `dt`。如果两次控制之间有时隔 1ms、有时隔 20ms（比如被打印日志卡住），同一个 Ki 参数的实际积分量就会忽大忽小——**你的 PID 参数就失效了**。固定周期 = 固定 dt = 参数意义稳定。

**周期多长合适？** 不是越快越好：

- 太快（比如 100kHz）：CPU 算不过来，PID 计算本身还没做完下一次又来了。
- 太慢（比如 10Hz）：云台手抖了 100ms 才反应，控制完全跟不上。
- 经验值：电流环 10~20kHz（电调内部做）、速度环/云台位置环 1kHz、温度/功率监控 10~100Hz。**1kHz 是位置/速度控制环的甜点位。**

**整车常见周期一览（经验值，具体以战队代码为准）：**

| 功能 | 周期 | 频率 | 为什么 |
|---|---|---|---|
| 电流环（电调内部） | 0.05~0.1 ms | 10~20 kHz | 电流变化极快，必须更快 |
| 云台/底盘控制环 | 1 ms | 1 kHz | 响应快又不浪费 CPU，PID 甜点位 |
| 状态机 / 遥控解析 | 10 ms | 100 Hz | 人的操作最多每秒几十次，10ms 足够 |
| 心跳 / 超时检查 / 功率监控 | 1000 ms | 1 Hz | 只是「保底检查」，1 秒一次足够 |

记住这个规律：**越靠近执行器，周期越快；越靠近「人的节奏」，周期越慢。**

**1kHz 控制任务在干什么？** 每 1ms：读反馈 → 算误差 → PID → 限幅 → 发指令。这个「读—算—发」的链路（概念四的 ④⑤⑥）必须在一个周期内完成。

**时间轴：不同频率的任务各占多少时间**

```
1kHz 控制任务： ██   ██   ██   ██   ██   ██   ██   ██   ██   ██   （每 1ms 一次，每次几十微秒）
100Hz 状态机：  ████████████                      ████████████      （每 10ms 一次）
1Hz 心跳：      ██████████████████████████████████████████████████ （每 1000ms 一次）
                ↑                                                  ↑
                0ms                                              1000ms
```

看到没有：1ms 的绝大多数时间其实是**空着的**——这就是 RTOS 存在的意义（概念八）：空闲时间可以分给别的任务。

**怎么实现固定周期？两种方案及取舍：**

方案 A：**硬件定时器中断**（裸机/RTOS 通用）

```c
/* 1ms 定时器中断：到点就进 ISR，置标志位 */
volatile uint32_t tick_1ms = 0;

void TIMx_IRQHandler(void)   /* 每 1ms 由硬件触发一次 */
{
    tick_1ms++;                       /* 只做一件事：数拍子 */
    gimbal_control_pending = 1;       /* 通知主循环/任务：该跑控制了 */
}

int main(void)
{
    /* ...初始化... */
    while (1) {
        if (gimbal_control_pending) { /* 主循环里执行真正的控制 */
            gimbal_control_pending = 0;
            Gimbal_Control_1kHz();
        }
    }
}
```

- 优点：周期极准（硬件节拍器，抖动用微秒算）、不依赖操作系统、开销小。
- 缺点：主循环里如果有一段慢代码，控制就会「跳拍」；逻辑复杂后主循环会越来越挤。

方案 B：**RTOS 定时任务**（见概念八）

```c
void GimbalTask(void *arg)
{
    TickType_t last = xTaskGetTickCount();        /* 记住上次时刻 */
    for (;;) {
        Gimbal_Control_1kHz();                    /* 执行控制 */
        vTaskDelayUntil(&last, pdMS_TO_TICKS(1)); /* 等到距上次正好 1ms */
    }
}
```

- 优点：代码结构清晰，多个周期任务各占一个任务，互不挤占。
- 缺点：实际执行时刻比硬件中断「抖」一点（调度需要时间），极端情况下会延迟几微秒到几十微秒——对 1kHz 控制环通常够用；不够用的场合（如电流环）就用中断。

**战队实践**（讲解时结合战队现有代码展示）：打开工程，找控制周期任务的实现位置——是定时器中断，还是 RTOS 任务，周期是多少；对照本节两张图理解。

> **一句话总结：固定周期 = PID 的 dt 恒定 = 参数有意义；1kHz 用「定时器中断」或「RTOS 延时任务」实现，前者更准，后者更整洁。**

### 概念七：中断与 DMA——「快递敲门」与「搬运工」

1.3 节讲过中断（Interrupt）= 快递敲门：CPU 正在干一件事，硬件事件一来，先放下手里的活去处理（进中断服务函数 ISR），处理完再回来。这一节补两条**架构视角**的铁律：

**铁律一：ISR 必须短（微秒级）。** 因为 ISR 执行期间，同优先级及更低优先级的中断都被挡在门外，主循环/低优先级任务全部停摆。1kHz 控制任务正等着跑呢，你的 ISR 里如果放了个 5ms 的 `printf`，控制环当场乱掉。ISR 里只允许：收数据、置标志、发信号，然后立刻退出。

**铁律二：数据搬运交给 DMA（Direct Memory Access，直接存储器访问）。** DMA 是一个独立的「搬运工」：CPU 告诉它「把这块内存搬到那块内存，搬 N 字节」，它自己搬，搬完才用中断通知 CPU。串口收一串数据、ADC 连续采样、CAN 收多帧数据，都可以让 DMA 在后台搬，CPU 只在「一包搬完」时被打扰一次。

```
不用 DMA：CPU 亲自搬，每来一个字节就被打断一次（累死，还耽误 1kHz 控制）
  CPU：████搬运████  ████搬运████  ████搬运████ ...

用 DMA：CPU 只管布置任务，搬运工干完才来敲门
  CPU：布置▇ 算PID▇▇ 算PID▇▇ 算PID▇▇ 收包▇ 算PID▇▇ ...
  DMA：     ▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇▇（自己搬，不打扰）
```

**在数据流中的位置**（回看概念四）：中断把数据「收进门」，DMA 把数据「搬进仓库（缓冲区）」，Device 层从仓库取货。三者的分工：**DMA 搬数据，中断发通知，模块做计算。**

> **一句话总结：中断只收门、DMA 只搬运、计算交给模块层——ISR 一长，整个系统的心跳就乱了。**

### 概念八：RTOS 任务——「分时会议室」

**RTOS（Real-Time Operating System，实时操作系统）**：跑在单片机上的小型操作系统（如 FreeRTOS、RT-Thread），核心能力是把 CPU 时间「分」给多个**任务（Task）**。

**任务是什么？** 一段「看起来一直在独立运行」的函数——每个任务有自己的 `for(;;)` 循环和独立栈，像一个个互不干扰的小程序：

```c
void GimbalTask(void *arg)      /* 云台控制任务：1kHz */
{
    TickType_t last = xTaskGetTickCount();
    for (;;) {
        Gimbal_Control_1kHz();
        vTaskDelayUntil(&last, pdMS_TO_TICKS(1));
    }
}

void HeartbeatTask(void *arg)   /* 心跳任务：1Hz */
{
    for (;;) {
        Led_Toggle();                       /* LED 闪烁 = 系统活着 */
        Watchdog_Feed();                    /* 喂看门狗 */
        vTaskDelay(pdMS_TO_TICKS(1000));
    }
}

int main(void)
{
    /* ...硬件初始化... */
    xTaskCreate(GimbalTask,    "gimbal",    512, NULL, 3, NULL);  /* 优先级 3 */
    xTaskCreate(HeartbeatTask, "heartbeat", 128, NULL, 1, NULL);  /* 优先级 1 */
    vTaskStartScheduler();                  /* 交出控制权，调度器接管 */
    for (;;) {}                             /* 永远不会走到这里 */
}
```

**「分时会议室」类比**：CPU 是一间会议室，任务是想开会的人。

- 每个任务有**优先级（Priority）**：数字越大，级别越高（FreeRTOS 约定）。
- **抢占（Preemption）**：高优先级任务一到「开会时间」（延时到期、被信号唤醒），正在开会的低优先级任务立刻被请出去，会议室让给高优先级——这叫抢占式调度。
- **同优先级轮流**：同一级别的任务按时间片轮流用会议室，人人有份。
- **阻塞（Blocked）**：任务调用 `vTaskDelay` 时主动离开会议室去等（「我 1ms 后再来」），**等待期间不占 CPU**——这是它比「主循环里死等延时」高明的地方：死等的延时是白占 CPU，阻塞的延时是让出 CPU。
- 会议室没人用时，由系统自带的「空闲任务」（最低优先级）打扫卫生。

回到概念六的时间轴：1kHz 控制任务每 1ms 开一次「几十微秒的小会」，剩下 900 多微秒会议室空着，正好给状态机任务、心跳任务、裁判系统任务轮流用——**这就是整车几十个功能能「同时」跑的秘密**。

**任务 vs 中断**：中断是「硬件敲门，CPU 无条件立刻去」，任务之间是「按优先级商量着来」。所以紧急的、微秒级的事交给中断，周期性的、毫秒级的事交给任务。

| | 中断（ISR） | RTOS 任务 |
|---|---|---|
| 触发方式 | 硬件事件，无条件立刻打断 | 调度器按优先级安排 |
| 时间精度 | 极高（微秒级） | 良好（毫秒级抖动） |
| 能做的事 | 只收数据/置标志（必须极短） | 可做复杂计算、可阻塞等待 |
| 适合场景 | 数据到达、紧急保护、电流环 | 1kHz 控制、状态机、通信、UI |

**常见组合拳**：硬件中断负责「收数据 + 发信号」，RTOS 任务负责「算 + 控制」——两边各干各擅长的。战队工程里具体哪个功能用哪种方式，讲解时打开代码对照。

**战队实践**（讲解时结合战队现有代码展示）：框架用的是 **CubeMX 开启的 FreeRTOS**（CMSIS-RTOS v2 封装，延时函数是 `osDelay(1)` 而不是裸 `vTaskDelay`），控制任务的入口在 `components/Controller/ControllerTask.cpp`，周期为 1ms（1kHz）。本节示例用的是 FreeRTOS 原生 `xTaskCreate` / `vTaskDelayUntil` 写法，语义等价，具体以实际工程为准。

> **一句话总结：RTOS = 分时会议室；任务按优先级抢占 CPU，阻塞等待让出 CPU——「同时跑」其实是轮流跑得足够快。**

参考代码（可先抄后改）：

```c
#include <stdio.h>

typedef enum { OFF, INIT, FOLLOW, PROTECT } State_e;

static State_e state = OFF;
static const char *name[] = {"OFF", "INIT", "FOLLOW", "PROTECT"};

int main(void)
{
    char ev;
    printf("p=上电 c=标定完成 e=急停 r=解除 q=退出\n");
    while (scanf(" %c", &ev) == 1 && ev != 'q') {
        State_e next = state;              /* 先假设不转移 */
        switch (state) {
        case OFF:
            if (ev == 'p') next = INIT;
            break;
        case INIT:
            if (ev == 'c') next = FOLLOW;
            if (ev == 'e') next = PROTECT;
            break;
        case FOLLOW:
            if (ev == 'e') next = PROTECT;
            break;
        case PROTECT:
            if (ev == 'r') next = INIT;    /* 解除后重新标定 */
            break;
        }
        printf("[%s] event=%c -> [%s]\n", name[state], ev, name[next]);
        state = next;
    }
    return 0;
}
```

## 常见问题与排查

| 现象 | 可能原因 | 排查方法 |
|---|---|---|
| 状态机「卡死」在某一状态不转移 | 事件条件函数没写对；标志位被置位后没人清除；事件本身没发生 | 在转移语句处打断点，打印事件函数返回值；检查标志位清零点 |
| 1kHz 控制任务周期忽长忽短 | 任务里混入了阻塞延时；同优先级/更高优先级任务抢 CPU；ISR 过长 | 用 GPIO 翻转 + 示波器量周期；检查任务里的 `HAL_Delay`；缩短 ISR |
| 电机反馈值乱跳（转速忽大忽小） | Device 层解析字节序/量纲错了；缓冲区读写不同步（数据被覆盖） | 对照协议逐字节核对；给缓冲区加「读完再写」的保护（环形缓冲 + 索引检查） |
| 加了 RTOS 后程序随机死机 | 任务栈开太小（栈溢出）；优先级配置不合理；中断里调用了 RTOS 阻塞函数 | 增大任务栈并查溢出钩子；检查中断服务函数是否调用了 `vTaskDelay` 等 |
| 修改底层代码后云台行为诡异 | 上层直接依赖了底层实现细节（没走接口） | 回看接口是否被绕过；把对实现细节的访问改成走 Device/Module 接口函数 |
| 控制量输出没有限幅，电机发疯 | 控制器输出未做限幅（2.5 节重点讲） | 在发送前加输出限幅，观察现象是否消失 |

1. 违反了两条：ISR 必须短（铁律一），以及分层原则（遥控器解析属于 Device 层的事）。ISR 里只应把 CAN 数据收进缓冲区并置标志；解析工作放到 Device 层的解析函数里，由模块层周期调用。
2. 转移图见概念五。若比赛开始而云台仍在「初始化」，状态机因为没有收到「标定完成」事件而停留在 INIT——这是安全的：未标定的云台角度不可信，贸然跟随可能打人/打结构件。宁可错过开局的几秒，也不能带着错误零位上线。
3. PID 的积分项 = Ki × Σ(误差 × dt)，dt 从 1ms 变 2ms，同样时间内积分累计量翻倍，等效于 Ki 翻倍——参数全部失效，所以周期必须固定。
4. 0~30ms 内任务 B 每 1ms 被调度（约跑几十微秒），任务 A 在 0、10、20ms 处各跑一次（每次更久）。若 A 一次跑了 50ms：A 优先级更高，B 在这 50ms 内完全得不到 CPU，1kHz 控制中断档 50 拍——这就是「控制任务优先级必须够高」的原因。
5. 后者更符合分层。PID 属于 Module 层业务，电机协议解析属于 Device 层；混在一起意味着「换个电机型号就得改 PID 代码」，两层职责都破防。前者只有在一个永不更换的专用设备上才勉强可接受。
</details>
