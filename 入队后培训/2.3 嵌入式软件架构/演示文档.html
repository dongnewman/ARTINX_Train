为什么需要分层

单文件裸机程序的问题

  • 初始化、CAN 收发、PID、按键全在一个 main.c
  • 改一处要通读全文，牵一发动全身
  • 多人协作改同一文件，冲突频繁

整车工程的现实

  • 云台、底盘、摩擦轮、裁判系统、遥控同时工作
  • 几十个功能并行，需要明确的分工边界
分层架构（Layered Architecture）：按职责把代码组织成层级，每层只解决一类问题，层间按规则调用。类比公司分部门，规则见下页。

五层架构总览

层类比职责典型内容
Application 应用层总经理调度全局：谁在什么时候干什么main、任务创建、遥控/裁判分发
Module 模块层业务部门一个完整功能：状态机 + 控制器云台模块、底盘模块、功率模块
Device 设备层设备管理员一个具体外设：收发帧、解析协议电机设备、IMU 设备、遥控器设备
BSP 板级驱动物业寄存器与外设初始化时钟、GPIO、CAN、UART 配置
硬件大楼芯片、总线、执行器、传感器STM32、CAN 总线、3508 电机

铁律 只能向下调用；不跳级；同层不直连；唯一「向上」是回调。控制器（PID）属于 Module 层。

调用规则与回调

规则内容
只能向下上层调用下层；下层不得指挥上层
尽量不跳级Application 经 Module 做事；遥控器等公共 Device 可直达
同层不直连模块协作走 Application 中转或消息队列
唯一向上回调（Callback）：下层注册函数指针，事件发生时被调用
/* 合法「向上」：Device 注册回调 */
dev->on_feedback = Module_OnMotorData;
/* ISR 只调回调，不关心上层是谁 */
放错层信号：BSP 里出现「云台」字样；Module 直接写寄存器；数据靠 extern 全局变量传递。

BSP 与 Device：物业与设备管理员

BSP（Board Support Package，板级支持包）

  • 把寄存器操作封装成函数：HAL_GPIO_WritePin(...)
  • 被 Device 调用；只碰硬件寄存器
  • 判断标准：不应出现任何业务名词（云台/底盘）

Device（设备层）

  • 管理一个外设的完整生命周期
  • 对外 = struct 数据 + 操作函数，隐藏协议细节
  • 被 Module 调用；调用 BSP
  • 维护设备状态字段与时间戳
设备 = 一个 struct + 一组函数：初始化 / 发送指令 / 解析反馈（如 Motor_Device_Init / SendSpeed / ParseFeedback）。

Module 与 Application：部门与总经理

Module（模块层）

  • 一个完整功能的家：状态机 + 控制器
  • 输入：Device 提供的数据；输出：控制量
  • 控制器（PID）住在这里，不属于单独一层
  • 被 Application 调用；调用 Device

Application（应用层）

  • 顶层：main 函数与 RTOS 任务创建
  • 决定「谁在什么时候干什么」
  • 遥控输入、裁判系统数据在此分发
  • 模块间协作在此中转

分层解决两件事：代码放哪里（职责）与谁能调谁（依赖方向）。

模块接口：一份「合同」

/* 云台模块接口：调用者只需知道两件事 */
void  Gimbal_SetTargetYaw(float yaw_deg);
float Gimbal_GetCurrentYaw(void);

/* 内部用什么电机、什么 PID：不暴露 */

接口 = 外部可见的 struct 与函数签名；函数名、参数、返回值即合同条款。

  • 封装：只暴露「做什么」，不暴露「怎么做」
  • 换电机型号 → 只改 Device 内部，调用方零改动
  • 反例：extern 全局变量 = 谁都能改，出 bug 难定位 → 数据藏进 struct，只暴露操作函数
改内部不影响外部——这是判断接口好坏的标准。

数据流：电机转速的完整旅程

电调 ── CAN 反馈帧(0x200+ID, 8 字节) ──▶ CAN 外设
① 中断 ISR：帧收进缓冲区，置标志      （微秒级）
② DMA（可选）：大批量数据后台搬运，搬完通知
③ Device：解析 转速/角度/电流，打时间戳
④ Module：控制器读反馈 → 误差 → PID → 输出
⑤ Device：输出打包控制帧 → BSP 塞进 CAN 邮箱
⑥ 电调执行；1 ms 后下一帧再来
  • 中断不干重活：解析计算留给后面的层
  • 每层只做份内事：解析的不算 PID，算 PID 的不碰寄存器
  • 时间戳识别迟到数据：判断数据是 1ms 前还是 10ms 前（2.9 超时处理）
反向旅程：控制输出沿 Device → BSP 发出，整条链路闭环。

数据流各站分工与时间预算

站谁干什么耗时
硬件CAN 外设自动收帧进硬件 FIFO并行，不占 CPU
中断ISR帧搬进软件缓冲区，置标志微秒级
DMA搬运工大批量数据后台搬运，搬完通知并行
Device电机设备按协议解析转速/角度，打时间戳微秒级
Module云台控制器读反馈 → 误差 → PID → 输出几十微秒
BSP发送函数控制帧塞进 CAN 邮箱微秒级

时间预算 整条链路必须在一个控制周期（1 ms）内完成，剩余时间留给其他任务。

状态、模式、状态机：三个定义

状态（State）

系统某一时刻的确定工作情形，同一时刻只能是其中一种。

模式（Mode）

上层选定的工作方式（遥控/自瞄），决定目标值从哪里来。

状态机（State Machine）

「状态 + 事件 + 转移规则」的模型：只有事件发生，状态才转移。

一句话：模式是选择，状态是事实。云台状态：关机（OFF）/ 初始化（INIT）/ 跟随（FOLLOW），另有保护（PROTECT）。

云台状态转移图

               ┌──── 断电 ────┐
               ▼              │
 OFF ──上电──▶ INIT ──标定完成──▶ FOLLOW
               │  ▲              │
               │  │ 解除          │ 急停
               ▼  │              ▼
             PROTECT ◀───────────┘
  • 转移条件写在箭头上：事件触发转移
  • 没收到「标定完成」，永远留在 INIT——未标定角度不可信，贸然跟随会失控
  • 新需求 = 加一个状态、加几条转移，逻辑不散落
状态跳跃逻辑（标定/跟随/保护）用 if 堆叠不可维护，状态机一张图讲清。

switch 状态机（上）：枚举与前半

typedef enum { OFF, INIT, FOLLOW, PROTECT }
  State_e;
static State_e state = OFF;   /* 当前状态 */

void FSM_Update(void) {    /* 每周期调用 */
  switch (state) {
  case OFF:
    if (PowerOn()) state = INIT;   /* 上电 */
    break;
  case INIT:
    Calibrate();
    if (CalibDone())     state = FOLLOW;
    if (EmergencyStop()) state = PROTECT;
    break;
  • 枚举给每种状态一个名字
  • state 用 static 限定：仅本文件可见，外界改不了
  • 每个 case：做本状态的事 + 检查事件

switch 状态机（下）：后半与要点

  case FOLLOW:
    FollowControl();             /* 每周期跟随控制 */
    if (EmergencyStop()) state = PROTECT;
    break;
  case PROTECT:
    MotorRelax();                /* 电机放松 */
    if (!EmergencyStop()) state = INIT;
    if (!PowerOn())       state = OFF;
    break;
  default: state = OFF;       /* 兜底 */
  }
}
  • 转移 = 改 state：下一拍走新 case
  • default 兜底：未知值回安全态（关机）
  • 状态机每周期调用一次（100 Hz 即可）

控制周期：定义与常见周期

  • 控制周期（Control Period）：控制器以固定间隔执行，该间隔即控制周期；云台/底盘常用 1 kHz（1 ms）。
  • 为什么固定：PID 积分项乘 dt、微分项除 dt；dt 波动 → 同一组参数实际效果漂移 → 控制失效。
功能周期频率依据
电流环（电调内部）0.05~0.1 ms10~20 kHz电流变化极快，必须更快
云台/底盘控制环1 ms1 kHz响应速度与 CPU 负载的平衡点
状态机 / 遥控解析10 ms100 Hz人的操作节奏最多几十 Hz
心跳 / 超时 / 功率监控1000 ms1 Hz保底检查，每秒一次足够

规律：越靠近执行器周期越快，越靠近人的节奏越慢。

1kHz 时间轴与两种实现

1kHz 控制 每 1 ms 一拍：读 → 算 → 发
100Hz 状态机
1Hz 心跳 每 1000 拍执行 1 次（本窗口看不见）
方案触发方式精度适用
中断定时硬件定时器微秒级电流环、数据到达
RTOS 任务调度器毫秒级抖动1kHz 控制、状态机、通信
中断里只置标志，控制逻辑放主循环/任务——两者常组合使用。

中断与 DMA

中断（Interrupt）

  • 硬件事件打断当前执行流，转入中断服务函数（ISR）
  • ISR 必须短（微秒级）：只收数据 / 置标志 / 发信号
  • 禁止：printf、延时、复杂计算——ISR 期间同级中断被挡

DMA（Direct Memory Access）

  • 直接存储器访问：独立硬件搬运工
  • CPU 布置任务（源/目标/字节数），搬完用中断通知
  • 适合：串口批量接收、ADC 连续采样、CAN 多帧
分工：DMA 搬运、中断通知、模块计算。ISR 一长，1kHz 控制环当场乱拍——整车最经典的坑。

RTOS 任务：五个关键概念

概念定义
RTOS实时操作系统（Real-Time OS），运行在 MCU 上，核心能力是多任务调度（FreeRTOS / RT-Thread）
任务（Task）独立执行流：各自 for(;;) 循环 + 独立栈，像并行的小程序
优先级（Priority）数字越大级别越高（FreeRTOS 约定），调度器永远运行最高优先级的就绪任务
抢占（Preemption）高优先级任务就绪（延时到期/被唤醒）时，立即打断正在运行的低优先级任务
阻塞（Blocked）任务调用 vTaskDelay 主动离开等待，不占 CPU；与死等延时（白占 CPU）的区别所在

类比一句话：CPU 是分时会议室，优先级是级别，抢占是「大佬到了让位」。

RTOS 固定周期任务示例

void GimbalTask(void *arg) {
  TickType_t last = xTaskGetTickCount();
  for (;;) {
    Gimbal_Control_1kHz();         /* 执行控制 */
    vTaskDelayUntil(&last,
        pdMS_TO_TICKS(1));        /* 距上次正好 1ms */
  }
}
xTaskCreate(GimbalTask, "gimbal", 512,
             NULL, 3, NULL);      /* 优先级 3 */
vTaskStartScheduler();          /* 交给调度器 */
  • vTaskDelayUntil：补偿执行耗时，保证固定周期
  • 第三个参数 512 是任务栈大小（字）
  • 任务函数永不 return

本节回顾

  • 五层架构：Application / Module / Device / BSP / 硬件，只能向下调用，回调例外
  • 接口是合同；数据流一条链：中断 → DMA → Device → Module → 控制器
  • 状态机 = 状态 + 事件 → 转移；控制周期固定，PID 参数才有意义
  • 中断收门、DMA 搬运；RTOS = 优先级抢占 + 阻塞让出 CPU
