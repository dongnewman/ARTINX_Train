# 2.7 调试与问题定位

> 本节目录 / 建议课时：90 分钟（讲课 45 + 实操 45）｜前置要求：2.3 嵌入式软件架构

机器人不会说话。它出问题时，只会用三种方式告诉你：**不动、乱动、报错**。这一节教你的不是某个具体 bug 的解法，而是一套「像医生问诊一样」的调试方法：先分层、再定位，用证据说话——把「它为什么不动」变成「我查到了是哪一层、哪一个信号、哪一行的问题」。

---

## 学习目标

- [ ] 能背出八步调试流程：现象 → 分层 → 假设 → 证据 → 缩小 → 定位 → 修复 → 验证
- [ ] 能按「整车 → 子系统 → 模块 → 信号 → 代码」五层给问题分层，并说出每一层怎么排除
- [ ] 会看电调指示灯、用万用表量电压/通断、用 CAN 工具抓帧判断总线是否正常
- [ ] 会用 Keil 断点 + Watch 窗口观察变量，用串口打印辅助定位
- [ ] 能把 CAN 日志导出成 CSV，用 Python + matplotlib 画曲线找规律
- [ ] 面对「电机不转 / CAN 掉线 / IMU 异常 / 遥控器异常 / 整车异常」，能按症状清单排出最可能原因并逐项排查
- [ ] 建立证据意识：下结论前先拿数据；改动前先留记录

## 核心概念

### 概念一：调试是什么——给机器人「做体检」

**生活类比**：你头疼去医院，医生不会直接开药。他会先**问症状**（什么时候疼？怎么个疼法？），再**做检查**（量体温、拍片子），把范围从「整个人」缩小到「某个器官」，最后才开药。调试（Debug）就是给机器人做这套问诊。

**定义**：调试 = 发现程序或电路「哪里没按预期工作」→ 找到原因 → 修复 → 验证的过程。「bug」这个词的来源很有意思：1947 年，哈佛 Mark II 计算机出故障，工程师真的在继电器里夹出一只飞蛾（moth），把它贴在日志本上并注明「史上第一个真实被抓到的 bug」——从此「找 bug」成了程序员的日常。

**机器人调试和纯软件调试的三个区别**：

1. **问题可能在硬件**：不一定是代码错，可能是线断了、没供电、电机本体坏了。
2. **只能靠观察**：机器不会告诉你「第 128 行写错了」，只能通过症状和数据推理。
3. **环境会捣乱**：场地震动、静电、线材老化，都会制造「时好时坏」的玄学问题。

**一句话总结**：调试 = 问诊式定位——通过现象、分层、证据，把「哪里坏了」从整车一路缩小到一行代码或一根线。

### 概念二：分层定位法——「先分层，再定位」

**生活类比**：家里突然没网了。你不会一上来就重装系统，而是逐层排查：先看路由器灯亮不亮（设备层）→ 再看手机能不能上（网络层）→ 再查是不是欠费（服务层）→ 最后才怀疑自己电脑设置（本机层）。**从大到小、一层层排除，每层都有明确的检查动作**——这就是分层定位。

**五层模型**：把机器人从大到小分成五层，问题一定落在其中某一层：

```
   整车    ──  整车上电、其他功能、公共电源
     │
   子系统  ──  一条 CAN 总线、一块供电域、一个执行机构组
     │
   模块    ──  单个电机 + 电调、单块板卡、单个传感器
     │
   信号    ──  CAN 帧、PWM 波形、电压、时序
     │
   代码    ──  发送函数、参数、状态机、逻辑判断
```

**每一层都要回答同一个问题：「我怎么证明这一层没问题？」** 以「1 号电机不转，其余电机正常」为例：

| 层 | 在这个案例里指什么 | 「这一层没问题」长什么样 | 排除动作 |
|---|---|---|---|
| 整车 | 整车上电、公共电源、主控 | 其他电机、云台、灯都正常 | 观察其他执行机构是否正常 |
| 子系统 | 底盘 CAN 总线、底盘供电 | 同一总线上其他电机有反馈 | 看其他电调指示灯 / CAN 工具抓帧 |
| 模块 | 1 号电机 + 它的电调 | 换一个已知好的电机转得起来 | 交叉替换：好的电机换过来试 |
| 信号 | CAN 帧、24V 供电电压 | CAN 工具抓到该电机的反馈帧；万用表量到 24V | 抓帧 / 量电压 / 看波形 |
| 代码 | 发送指令的函数与参数 | 断点停住、变量值符合预期 | 断点 + Watch / 二分法注释 |

**两条铁律**：

1. **先证明上层没问题，再往下钻。** 顺序反了会白忙——代码查了一下午，最后发现是电源没插。
2. **证明不了的层，用交叉替换。** 拿一个「确定是好的」部件换上去，问题消失 = 原部件坏，问题还在 = 往别处查。这就是为什么调车时要有备用的电机、电调和线材。

**五层在整车上的完整地图**（结合 2.6 节整车电气理解，具体设备以战队实车为准）：

```
 整车层    公共电源（电池 → 电源管理）、主控板、整车 CAN 主干
    │
 子系统层  底盘（4×电调+电机）、云台（yaw/pitch 电机）、发射、裁判系统、IMU…
    │
 模块层    单个电调+电机、单块板卡、单个传感器、单根线束
    │
 信号层    CAN 帧、24V/12V/5V 电压、PWM 波形、串口字节流、编码器信号
    │
 代码层    控制指令生成、状态机、参数、通信配置（波特率/ID/滤波）
```

**每一层的「典型问题长相」**——先看长相，再猜在哪层：

| 层 | 这层出问题时，通常长这样 |
|---|---|
| 整车 | 一切都不动 / 上电即异常 / 所有子系统同时挂 |
| 子系统 | 一个子系统的全部设备异常，其他子系统正常 |
| 模块 | 单个电机 / 单块板卡异常，同层其他设备正常 |
| 信号 | 模块供电正常、接线正常，但数据「对不上」 |
| 代码 | 硬件全好，行为不符合预期（该转不转、该停不停） |

**顺序错了会怎样**：跳过整车层直接查代码——查一下午「为什么没发指令」，最后发现是主控没上电；反过来，永远在整车层转悠，把所有模块都怀疑一遍，唯独不肯打开代码看看。分层定位的价值，就是用**最小的检查成本，砍掉最大的怀疑范围**。

**同一个案例，画成决策树长这样**（演示文档里可以逐层点选）：

```
现象：1 号电机不转
 └─ ① 主控发出指令了吗？──否──► 结论：代码没发指令（断点查调用链）
     └─是
       ② CAN 工具抓到指令帧了吗？──否──► ③ 电调灯亮吗？──否──► 供电问题（量 24V）
         └─是                            └─是──► 链路问题（查线/终端电阻）
           ④ 有该电调反馈帧吗？──否──► ★ 定位：CAN 波特率配置错（改回 1 Mbps）
             └─是
               ⑤ 反馈数据合理吗？──否──► 相线/编码器线（交叉替换）
                 └─是──► 指令数值问题（控制量=0 / 方向反）
```

注意：决策树上的每一次提问，背后都配了一个「证据动作」——断点、抓帧、看灯、量电压。**没有证据的提问是空转**：你没法知道答案该填「是」还是「否」。

**一句话总结**：先分层、再定位——像漏斗一样从整车开始一层层收窄，每层用「指示灯 / 抓帧 / 量电压」之类的证据排除，最终落在信号或代码上。

### 概念三：八步调试流程

**生活类比**：分层回答「在哪一层」，八步流程回答「接下来具体怎么走」。它是一条从「看到现象」到「确认修好」的流水线，新手最容易跳过的第 4 步（证据），恰恰是最重要的一步。

```
 ①现象 ──► ②分层 ──► ③假设 ──► ④证据 ──► ⑤缩小 ──► ⑥定位 ──► ⑦修复 ──► ⑧验证
```

**完整案例：「1 号电机不转」**（这个案例是本节的主线，演示文档里可以交互点选）：

**① 现象——描述得越具体越好。**
「上电后 1 号电机不转，其余 3 个正常。」注意「其余正常」本身就是关键证据：它一下子把整车层、子系统层都基本排除了。

**② 分层——问题大概在哪一层？**
整车其他功能正常 → 不是整车层；同一条 CAN 上其他电机正常 → 子系统层基本排除；问题缩小到「1 号电机这个模块」及以下（信号层、代码层）。

**③ 假设——列出最可能原因并排序。**
按概率排：A. 指令没发出去（代码层）；B. CAN 通信不通（信号层）；C. 电调供电异常（模块层）；D. 电机/电调本体损坏（模块层）。

**④ 证据——为每个假设设计一个验证动作。**
- 验证 A：Keil 断点看到发送函数确实被执行；
- 验证 B：CAN 工具挂到总线上抓帧——看有没有发给 1 号电调的帧、有没有它的反馈帧；
- 验证 C：看电调指示灯（供电 / CAN 状态的窗口）、万用表量 24V 电源；
- 验证 D：交叉替换一个好的电机。

**⑤ 缩小——根据证据排除假设。**
实测：发送函数被执行（A 排除）；电调指示灯常亮、24V 正常（C 排除）；CAN 工具能抓到主控发出的指令帧，但**电调没有任何反馈帧**——问题锁定在信号层：主控和电调在 CAN 上「说不上话」。

**⑥ 定位——找到具体原因。**
对照 CAN 配置逐个查：接线、ID、波特率……发现波特率配成了 500 kbps，而整车总线是 1 Mbps——主控喊话速度不对，电调听不懂，自然不理你。

**⑦ 修复——一次只改一个变量。**
把波特率改回 1 Mbps，重新编译烧录。

**⑧ 验证——回归验证，防止修出新问题。**
1 号电机正常转动，再把其余 3 个电机、云台、遥控都跑一遍，确认没把别的东西修坏。

**新手最常犯的错误**：直接从 ① 跳到 ⑦——「我猜是 XX，改了试试」，没好再猜下一个。少了「证据」，调试就变成买彩票。**每个假设必须配一个可执行的验证动作**，才允许进入下一步。

**每一步最常见的错误**：

| 步骤 | 常见错误 | 后果 |
|---|---|---|
| ① 现象 | 只说「电机不转」，不说哪台、何时、其他电机如何 | 排查范围=整车，效率极低 |
| ② 分层 | 跳过上层直接查代码 | 查一下午，发现是没上电 |
| ③ 假设 | 只列一个原因 | 一条路走到黑，错了推倒重来 |
| ④ 证据 | 跳过，直接「我觉得」 | 调试变买彩票 |
| ⑤ 缩小 | 证据不支持也硬下结论 | 方向错了，越查越远 |
| ⑥ 定位 | 找到第一处异常就停手 | 治标不治本，根因还在 |
| ⑦ 修复 | 一次改多处 | 不知道是谁治好的 |
| ⑧ 验证 | 只验证出问题的那一项 | 修好 A 弄坏 B，比赛才炸 |

> 提示：流程不是教条。问题一眼可见时（线头断了、灯不亮），直接修就好；流程的价值在于**查不出来时，给你一条不掉坑的路线**。

**第二个案例：IMU 数据乱跳（压缩版八步）**——体会同一套流程怎么套到不同问题上：

1. **现象**：云台启动后 Yaw 角每几秒跳一次，其他功能正常。
2. **分层**：其他正常 → 整车层排除；锁定云台子系统内的 IMU 模块与它的数据链路。
3. **假设**：① 线束虚接（云台转动时拉扯）；② 供电波动；③ 帧解析错位。
4. **证据**：重新插拔线束再测（验证①）；示波器看 IMU 供电纹波（验证②）；打印原始帧逐字节核对（验证③）。
5. **缩小**：插拔后依旧乱跳；供电波形干净；但原始帧里偶尔出现一个明显错乱的字节 → 通信链路问题。
6. **定位**：串口接线处插头氧化，云台转到特定角度时接触电阻突变，导致丢字节。
7. **修复**：更换插头并加固线束走线。
8. **验证**：云台全角度来回转动 10 分钟数据稳定；再跑一遍整车功能确认无影响。

看出规律了吗？**换的是问题，不变的是流程。**

**一句话总结**：八步流程 = 现象、分层、假设、证据、缩小、定位、修复、验证；第 4 步「证据」是承上启下的关键，跳过它就是纯靠运气。

### 概念四：证据意识——猜测必须用数据证实

这一节是整堂课的「价值观」部分：**没有证据的「我觉得」，都只是猜。**

**① 「玄学问题」大多有规律，只是触发条件没找到。**
「这个电机有时不转，有时又好好的」——听起来像玄学，其实是某个触发条件没被你发现（比如：刚上电的前 5 秒会掉帧？只有满电时出现？只有连续急停后出现？）。方法：**每次出现都记录当时的全部条件**（时间、电量、上一个动作、现场环境），多攒几次，找交集。规律就藏在交集里。

**② 一次只改一个变量。**
同时改三处：好了不知道是谁的功劳，坏了不知道是谁的锅。正确姿势：改一处 → 验证 → 再改下一处。

**③ 记录「我改了什么」。**
改之前留一份能跑的版本（用 Git！见 1.6 节），每次改动写一行说明。查不出问题时，「回退到上一个正常版本」是最快的定位手段——它能把问题范围瞬间切成「新改动引入」或「一直存在」。

**④ 最小复现程序。**
在干净的、只有几行代码的小工程里复现问题。小工程里也出问题 → 大概率是硬件或底层配置；小工程里没问题 → 问题在你的业务代码里。这一步能把「自己写的代码」和「别人写的代码」切开。

**⑤ 二分法注释（缩小代码范围的利器）。**
把可疑代码注释掉一半：
- 问题消失 → 问题在被注释的那一半里；
- 问题还在 → 问题在没注释的那一半里。
对剩下的可疑部分继续对半……在 1024 行代码里定位一行，最多只需要 10 次。

**⑥ 复现问题：先回答三个问题。**

任何一次故障，第一时间记下三个答案：**何时**（刚上电？跑 3 分钟后？急停之后？）、**何条件**（满电？某台电机在转？有外接设备？）、**何表现**（完全不转？转了 1 秒停？抖动？）。这三点是所有排查的原材料，也是「玄学问题」破案的关键——把两次、三次、五次故障的三要素摆在一起，**交集就是触发规律**。

**证据也有强弱之分**：

- 弱证据：「我记得上次好像也是这样」——记忆会骗人；
- 中证据：「指示灯现在不亮」——实时观察，但转瞬即逝；
- 强证据：CAN 工具抓到的帧、示波器截图、日志 CSV、万用表的读数——**可回放、可对比、可给别人看**。

排查时优先收集强证据：截图、存日志、记录读数。**每一次下结论前，都要能回答：「你当时凭什么这么判断？」**

**一句话总结**：猜测必须用数据证实；「玄学」背后是没找到的触发条件；一次只改一个变量、每次改动留记录。

### 概念五：常用工具矩阵——八种工具，各管一段

先看总表，再逐个认识。**工具选对，排查快十倍**：

| 工具 | 能看什么 | 什么时候用 | 怎么上手 |
|---|---|---|---|
| 万用表 | 电压、通断、电阻 | 怀疑供电 / 线路断了 | 电压档表笔并联被测点；通断档两表笔碰线听蜂鸣 |
| 示波器 | 信号波形、频率、幅值 | 怀疑信号质量 | 探头接信号线，按 AUTO 自动抓波形 |
| 逻辑分析仪 | 多路数字信号的时序 | 协议时序（如 SPI、I2C） | 探头夹到信号线，软件里设触发抓取 |
| CAN 工具 | 总线帧的 ID 与数据 | CAN 不通 / 电机无反馈 | 设对波特率接入总线，看收发 |
| 串口工具 | printf 打印的日志 | 想看程序「走到哪一步」 | 波特率设置一致，打开串口收数据 |
| Keil Debug | 变量值、断点、调用栈 | 代码逻辑错误 | 光标行按 F9 打断点，F5 运行到断点 |
| Log 日志 | 事后回放的历史数据 | 偶发问题复盘 | 程序里定时存 CSV，带时间戳 |
| Python | 大量数据里的规律 | 数据曲线分析 | 读取 CSV，用 matplotlib 画图 |

**逐个认识**：

**万用表——医生的体温计。** 调车第一步经常是它：量电调供电是不是 24V、量 CAN_H 与 CAN_L 对地电压、通断档检查线是不是断了。便宜、直接、人人会用。

**示波器——给信号拍照片。** 万用表只能告诉你「大概有电」，示波器能让你**看见**波形长什么样：CAN 差分波形是否对称、PWM 有没有、频率对不对。新手用法：探头接上，按 AUTO，先让波形出现在屏幕上再说。

**逻辑分析仪——给多根线拍「连拍」。** 同时记录多路数字信号随时间的变化，专门查时序问题：某条协议线上有没有数据、先后顺序对不对。CAN 总线调试一般用 CAN 工具更直接，逻辑分析仪更多用于 SPI、I2C 这类板级协议。

**CAN 工具——总线的「监听耳机」。** 挂到总线上能**看到每一帧**：谁发的、ID 多少、数据是什么。判断 CAN 问题它是第一选择：收不到电调反馈帧，立刻就能区分「主控没发」「发了没人理」还是「总线根本没数据」。

**串口工具——程序的「日记本」。** 在代码里加 `printf`，把程序走到哪、变量是多少打印出来。适合查「流程问题」：为什么这个分支没进、这个函数没执行。

**Keil Debug——暂停世界，看变量。** 断点让程序**暂停**在任意一行，Watch 窗口实时显示变量值，还能单步执行一行一行看。查代码逻辑，这是最直接的显微镜。

**Log 日志——行车记录仪。** 机器人上赛场没法一直插着电脑，把关键数据定时存进日志（CSV），比赛回来**回放**分析：是哪个瞬间开始抖的？当时指令是什么？

**Python——数据分析师。** 几百 MB 的日志，肉眼看不完。Python 读进来，matplotlib 画成曲线，异常点、规律、趋势一目了然。这是本节动手实践任务三的内容。

**三分钟上手顺序**：新手先练前三样——万用表（安全第一，先会量电压与通断）、串口打印（零成本看流程）、Keil Debug（查逻辑的显微镜）；CAN 工具在电机调试时几乎每天都要用；示波器、逻辑分析仪在 2.6 节整车电气之后慢慢熟悉；Log 与 Python 是「赛后复盘」神器，先收藏、后精通。

**选工具口诀**：先量电（万用表）、再看灯（指示灯）、能抓帧不猜帧（CAN 工具）、能断点不肉眼（Keil Debug）、事后靠日志（Log / Python）。

**一句话总结**：量电用万用表、看波形用示波器、抓时序用逻辑分析仪、查总线用 CAN 工具、看流程用串口打印、查逻辑用 Keil Debug、复盘用 Log、找规律用 Python。

## 动手实践

> 实践用到的硬件以战队现有调试环境为准（讲解时结合战队现有代码与工具演示）。三个任务从代码层到数据层，正好覆盖五层模型的下三层。

### 任务一：二分法注释，把「电机不转」缩到一行

**目标**：用二分法注释，在 10 分钟内把一个「电机不转」问题定位到具体代码行。

1. 准备：写一个让电机转的程序，故意埋一个 bug（例如：发送函数写在了一个永远进不去的 `if` 分支里）。烧录，确认电机不转。✔ 自查点：确认问题稳定复现（每次上电都不转）。
2. 第一刀：把主循环里**后半段**代码注释掉，重新编译烧录。看电机转不转。
   - 不转 → 问题在**没注释的前半段**里；转 → 问题在**注释掉的后半段**里。
3. 对剩下的可疑段落重复第 2 步，每次砍一半。✔ 自查点：每刀只切一半，且每次只改注释这一件事。
4. 直到剩下 1~3 行，肉眼读出 bug。✔ 自查点：能说出「为什么这行导致电机不转」。
5. 恢复全部注释，验证电机正常转。

> 提示：注释会让程序功能残缺，所以二分法只用于**定位**；定位完一定要把代码恢复原样再修。

### 任务二：Keil 断点 + Watch，观察变量「活」起来

**目标**：用断点暂停程序，用 Watch 窗口观察变量变化。

1. 准备：新建或打开一个带主循环的工程，加入下面这段代码（也可以基于 1.3 节的点灯工程）：

```c
volatile int tick = 0;          // volatile：告诉编译器别把它优化掉

int main(void)
{
    /* ...外设初始化代码省略... */

    while (1)
    {
        tick++;                 // ① 在这里打断点
        if (tick > 100)
        {
            tick = 0;           // ② 在这里打断点
            LED_Toggle();       // 换一个灯的状态，肉眼验证程序活着
        }
        Delay_ms(10);
    }
}
```

2. 打断点：光标停在 `tick++;` 这行，按 <kbd>F9</kbd>（Keil 默认快捷键，以讲解演示为准），行首出现红色圆点。给 `tick = 0;` 也打一个。
3. 进入调试：点 Debug（或 <kbd>Ctrl+F5</kbd>）开始仿真。程序会**暂停在第一个断点**。✔ 自查点：黄色箭头停在断点行上。
4. 打开 Watch 窗口：右键变量名 `tick` → Add to Watch。按 <kbd>F5</kbd> 全速运行，观察 `tick` 的值不断变化，到 101 时停在第二个断点。✔ 自查点：Watch 里的值和你的预期一致。
5. 试试单步：按 <kbd>F11</kbd>（Step Into）一行一行执行，看 `tick` 每步 +1。✔ 自查点：能解释单步与全速的区别。
6. 思考：如果电机不转，你想确认「发送函数有没有被调用」——断点应该打在哪？试试。

> 硬件在线调试（连 ST-Link 的 STM32 板）同理：Debug 设置里选对调试器即可（讲解时演示）。

> **断点不生效？三个最常见原因**：① 编译优化等级过高，变量被优化掉（临时把优化等级改回 -O0）；② 断点打在了不会被执行到的代码上（先确认这段代码真的会跑）；③ 工程没生成调试信息（Options for Target → Output 里的 Debug Information，讲解时演示）。

### 任务三：用 Python 画 CAN 日志曲线，肉眼找规律

**目标**：把日志 CSV 画成曲线，找出「电机异常」发生的时刻与规律。

1. 准备：确认电脑装了 Python（`python --version`），并安装绘图库：`pip install matplotlib`。
2. 造数据：写一个小程序，让电机按正弦规律变速，同时通过串口把「时间、转速、电流」打印出来（或直接读取现有 CAN 日志，讲解时结合战队现有日志格式）。保存为 `motor_log.csv`，格式如下：

```csv
time_ms,rpm,current
0,0,100
10,120,300
20,260,520
...
```

3. 写绘图脚本 `plot_log.py`：

```python
# plot_log.py —— 把电机日志画成曲线，肉眼找规律
import csv
import matplotlib.pyplot as plt

rows = []
with open("motor_log.csv", encoding="utf-8") as f:
    for row in csv.DictReader(f):
        rows.append((float(row["time_ms"]),
                     float(row["rpm"]),
                     float(row["current"])))

t = [r[0] for r in rows]      # 时间
rpm = [r[1] for r in rows]    # 转速
cur = [r[2] for r in rows]    # 电流

plt.figure(figsize=(10, 6))
plt.subplot(211)                        # 上图：转速
plt.plot(t, rpm, color="tab:blue")
plt.ylabel("rpm")
plt.grid(True)
plt.subplot(212)                        # 下图：电流
plt.plot(t, cur, color="tab:orange")
plt.ylabel("current")
plt.xlabel("time (ms)")
plt.grid(True)
plt.tight_layout()
plt.show()
```

4. 运行 `python plot_log.py`。✔ 自查点：两张曲线图正常弹出，横轴时间、纵轴数值正确。
5. 分析：故意在日志里插入一段异常（例如某段时间转速掉到 0）。观察曲线，回答：异常从第几毫秒开始？持续多久？发生前电流有没有先异常？✔ 自查点：能指出异常区间并说出前后数据的关系——这就是「从数据里找触发条件」。

> 调试思路升级版：把「目标转速」和「实际转速」画在同一张图上对比，一眼看出「是没执行，还是执行错了」。
>
> 画图的三种排查套路：① **对比图**（目标 vs 实际，看执行对不对）；② **散点找异常**（数据里孤立的异常点就是故障时刻）；③ **时间窗放大**（只画故障前后 ±2 秒，细节全出来了）。

### 任务四：整车级排查演练——按五层走一遍

**目标**：在真实整车（或调试平台）上，完成一次从现象到修复的完整排查。

1. 由组长（或同伴）给整车埋一个「故障」：拔掉一个电调的 CAN 线、或断开某电调供电、或在代码里注释掉发送函数（三选一，不告诉你）。
2. 你从「上电观察」开始：描述现象——哪些功能正常、哪个不正常。✔ 自查点：现象里必须包含「其余正常」这类排除性描述。
3. 分层：按五层模型说出问题可能在哪一层，并给出理由。✔ 自查点：理由必须引用证据（如「其余电机正常，所以整车层排除」）。
4. 设计验证动作并执行：指示灯、万用表、CAN 工具、断点，至少用到其中两种。✔ 自查点：每个动作执行前先写下「如果结果是 X，说明什么」。
5. 定位到具体原因，向组长报告。✔ 自查点：报告格式 =「现象 → 证据 → 结论」，三句话以内。
6. 修复并回归验证：修好后把整车基本功能跑一遍。✔ 自查点：除被埋故障的功能外，其他功能未受影响。

## 常见问题与排查

> 使用说明：先对照「症状清单」确认现象，再按「最可能原因」从 1 到 5 逐项排查。顺序是统计意义上的概率排序，**不代表可以跳过证据**——每一项都要用对应工具验证。

### 典型问题一：电机不转

| 症状清单 | 说明 |
|---|---|
| 上电完全无反应 | 无声音、无力矩、指示灯异常 |
| 指示灯不亮 | 电调指示灯灭 = 供电 / 电调本体问题 |
| 灯亮但不转 | 供电与电调基本正常，怀疑指令与通信 |
| 抖动或异响后自锁 | 相线接错 / 堵转保护触发 |

**最可能原因排序**：

1. **供电问题**——24V 没送到电调 / 接线松动 / 保险丝断 → 万用表量电压、看指示灯。
2. **CAN 通信问题**——波特率不匹配、接线或 ID 错误 → CAN 工具抓帧：有没有指令帧、有没有反馈帧。
3. **指令没发出**——代码没调用发送函数 / 控制量为 0 → Keil 断点 + Watch。
4. **电调保护触发**——过流 / 堵转后保护自锁 → 观察指示灯报错状态，断电重新上电。
5. **电机本体损坏**——交叉替换一个已知好的电机验证。

### 典型问题二：CAN 掉线

| 症状清单 | 说明 |
|---|---|
| 所有电机同时失去反馈 | 总线级故障，不是单个模块 |
| 周期性掉线又恢复 | 疑似接触不良或干扰 |
| 一启动某设备就掉线 | 该设备拉死总线 / 总线冲突 |
| 单台设备无反馈 | 该设备接线 / 地址 / 波特率问题 |

**最可能原因排序**：

1. **终端电阻缺失或阻值错误**——总线两端必须有匹配的终端电阻（以 2.6 节整车电气为准），反射会破坏通信。
2. **接线接触不良**——杜邦线松动、焊点虚焊 → 万用表通断档逐段量。
3. **波特率不一致**——新接入的设备波特率与总线不符。
4. **某设备故障拉死总线**——逐个断开设备，看总线是否恢复（排除法）。
5. **主控程序异常**——看门狗复位 / 中断风暴 → 串口打印看程序是否还活着。

### 典型问题三：IMU 数据异常

| 症状清单 | 说明 |
|---|---|
| 数据完全不变 | 通信中断 / 初始化失败 |
| 数据乱跳、无规律 | 供电波动 / 接线接触不良 |
| 数据缓慢漂移 | 未校准 / 传感器特性 |
| 上电自检失败 | 接线 / 通信 / 器件问题 |

**最可能原因排序**：

1. **接线接触不良**——IMU 线束在云台转动时反复弯折，最易虚接 → 重新插拔线束、检查焊点。
2. **供电波动**——IMU 对电源纹波敏感，供电不稳数据就乱 → 示波器看供电波形。
3. **初始化 / 校准流程错误**——上电顺序、校准步骤不符合器件要求（以器件手册为准）。
4. **帧解析错位**——串口收数据丢字节或取错偏移，导致数值错乱 → 打印原始帧人工核对。
5. **机械震动与电磁干扰**——安装位置松动、靠近大电流线路。

### 典型问题四：遥控器异常

| 症状清单 | 说明 |
|---|---|
| 完全收不到遥控数据 | 接收机 / 串口问题 |
| 数据延迟明显 | 传输链路 / 程序处理慢 |
| 摇杆数值乱跳 | 接触不良 / 干扰 |
| 摇杆不动时数值漂移 | 校准问题 |

**最可能原因排序**：

1. **接收机接线与供电**——线序接反、供电不足是最常见的 → 万用表量接收机供电。
2. **串口波特率不匹配**——主控与接收机波特率必须一致。
3. **协议解析错误**——帧头、校验、字节序处理不对 → 打印原始数据逐字节核对。
4. **无线干扰与距离**——场地电磁环境复杂，注意天线安装（讲解时结合规则要求）。
5. **遥控器电量**——低电量时输出可能不稳（以具体遥控器说明为准）。

### 典型问题五：整车功能异常

| 症状清单 | 说明 |
|---|---|
| 多个子系统同时异常 | 查公共部分：电源、主控、总线 |
| 一上电就异常 | 查上电顺序与初始化 |
| 跑一段时间后异常 | 查发热、松动、累计性错误 |
| 特定动作触发异常 | 查该动作关联的模块与资源冲突 |

**最可能原因排序**：

1. **公共供电**——多个子系统同时出问题，先查它们的公共电源：电压、载流能力、保险丝。
2. **主控系统异常**——程序崩溃 / 状态机卡死 / 看门狗反复复位 → 串口打印或指示灯判断。
3. **CAN 总线故障**——见「典型问题二」。
4. **模块间资源冲突**——两个模块争用同一个外设 / 中断优先级冲突（讲解时结合战队代码展示排查案例）。
5. **上电顺序 / 初始化依赖**——某个模块没等另一个模块就绪就开始工作。

## 课后自测

1. 电机的灯亮着、其他电机正常，但 1 号电机不转。按分层法，你会先看哪一层？设计三个具体的验证动作。
2. 「CAN 工具抓不到 1 号电调的反馈帧，但能抓到主控发出的指令帧」——这个证据把问题缩小到了哪一层？列出三个可能原因。
3. 队友同时改了「波特率」「CAN 滤波器」「发送频率」三处，电机好了。为什么说这个修复不可靠？正确做法是什么？
4. 「这个 IMU 有时候正常，有时候漂得厉害」——按「玄学问题」的处理方法，写出你的排查计划。
5. 说出八步调试流程，并指出新手最常跳过的是哪一步、会导致什么后果。
6. 一段 400 行可疑代码里藏着导致电机不转的 bug。用二分法注释，最多需要几次能把它锁定到 1 行？

<details><summary>参考答案</summary>

1. 整车层已排除（其他功能正常）；直接看模块层与信号层。验证动作举例：① 看 1 号电调指示灯（供电 / CAN 状态）；② 万用表量电调 24V 供电；③ CAN 工具抓 1 号电机反馈帧；④ 换一个已知好的电机交叉替换。
2. 缩小到「信号层」：主控会发，电调没回。可能原因：① 波特率不匹配（电调听不懂）；② 指令帧 ID / 格式不对（电调不认）；③ 电调 CAN 侧接线或供电问题；④ 电调本体故障。逐一用工具验证。
3. 一次改三个变量，好了不知道是谁治好的；而且可能掩盖了新问题。正确做法：一次只改一个变量，改一处验证一次；用 Git 记录每次改动。
4. ① 每次出现时记录时间、供电方式、云台动作、环境等全部条件；② 攒 5 次以上，找共同点（交集）；③ 对共同点设计验证实验，主动复现；④ 复现后按八步流程定位。
5. 现象→分层→假设→证据→缩小→定位→修复→验证。最常跳过「证据」：没有证据就改，变成猜彩票，改了没好再猜下一个，永远建立不起因果关系。
6. 二分法每次砍一半：400→200→100→50→25→13→7→4→2→1，最多约 9 次（每次都要重新编译烧录并验证）。
