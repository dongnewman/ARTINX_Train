## 核心概念

### 概念一：能运行 vs 能稳定运行

**先给结论：「能运行」是及格线，「能稳定运行」才是上赛场的入场券。**

前面八节你已经能让车跑起来了：遥控器一推，底盘动；拨杆一打，云台转。这叫做「能运行」——**一切正常时它能动**。

但赛场上，「一切正常」从来不是常态：

- 比赛打到一半，裁判系统离线了
- 对手一撞，一个电机的 CAN 线松了
- 云台被按在地上，电机堵转，电流飙升
- 电池电量下降，电压掉了 2V
- 无线环境嘈杂，遥控器数据断断续续

「能稳定运行」的意思是：**任何环节出问题时，它要么继续工作、要么安全停下，绝不失控**。失控的代价不是「这次没打好」——是撞坏机械、烧掉电调、甚至伤到人。RM 场地上的车都是几十公斤的金属，失控冲出去就是事故。

```
能运行：     输入 → 输出 → 一切正常，能动            （只在晴天走路）
能稳定运行：  任何环节异常 → 检测 → 保护 → 安全停下  （晴天雨天都能走）
```

> **一句话总结：能运行 = 一切正常时它能动；能稳定运行 = 任何环节出问题时它要么继续工作、要么安全停下，绝不失控。赛场上的问题都不是假设。**

### 概念二：Timeout —— 等不到反馈，就降级

**先给结论：Timeout（超时）是「等不到就降级」的纪律：超过约定时间没收到新数据，就按最坏情况处理。**

类比：你给队友发消息问「明天几点集合」，如果对方一直不回，你会怎么办？你不会一直干等——你会**先按原计划行动**。这就是超时处理：**设置一个等待期限，到期没结果就执行备用方案。**

在机器人里，每一个「期待数据到达」的地方，都要有一个超时判断：

| 等待什么 | 超时多久算异常 | 超时后做什么 |
|---|---|---|
| 遥控器新数据 | 100ms | 急停（停止所有运动） |
| 电机 CAN 反馈 | 200ms | 该电机断电（电流置 0） |
| 裁判系统数据 | 1s | 降级：停止射击，保留运动 |
| 上位机（视觉）指令 | 500ms | 保持最后目标或进入自动模式 |

实现上只需要一个「喂狗」动作：**每收到一次数据，就记下当前时间；每个控制周期检查「现在 − 上次收到的时间」是否超过阈值**。

```c
/* 遥控器数据超时检查（每 1ms 控制周期执行一次） */
#include <stdint.h>
#include <stdbool.h>

static uint32_t now_tick    = 0;   /* 由 1ms 定时器中断累加 */
static uint32_t last_rc_tick = 0;  /* 上次收到遥控器数据的时间 */
static int16_t  target_speed = 0;

#define RC_TIMEOUT_MS   100u        /* 遥控器 100ms 没新数据 → 断联 */

/* 遥控器数据接收回调（每收到一帧调用一次） */
void on_rc_data(int16_t speed)
{
    last_rc_tick = now_tick;        /* 喂狗：刷新最后收到时间 */
    target_speed = speed;
}

void control_loop(void)
{
    /* 无符号减法天然处理时间回绕，比 > 号更安全 */
    if ((uint32_t)(now_tick - last_rc_tick) > RC_TIMEOUT_MS) {
        target_speed = 0;           /* 超时 → 急停，绝不保持旧指令 */
    }
    send_current(target_speed);
}
```

几个关键细节：

- **用无符号减法判断超时**：`(uint32_t)(now - last) > THRESHOLD`。即使 `now_tick` 从 0xFFFFFFFF 回绕到 0，这个式子依然正确，比 `now > last + THRESHOLD` 更稳。
- **超时后置 0，而不是「保持最后指令」**：保持最后指令 = 遥控器断联后车还全速冲。安全的第一选择永远是停下来。
- **喂狗的位置要对**：必须在「数据真的有效」之后才喂狗，收到一包乱码不算数。

> **一句话总结：每等一个数据，就问一句「多久没来了」；超过约定时间，立刻按最坏情况处理。**

### 概念三：Output / Input Limit —— 进出都设边界

**先给结论：输出要限幅（Out Limit），输入要验真（In Check）——数据进出系统的两道门，谁都不能裸奔。**

#### 输出限幅（Output Limit）

你的 PID 算出来的输出可能远超电机承受范围：误差很大时，P 项输出可能是 100000，而电调最大电流只收 16384。如果不限幅，溢出会直接把你算出来的值截断成负数——**电机瞬间反转**，这就是很多「电机突然抽风」的元凶。

**所有发给执行器的量，在发送前必须压进允许范围**：

```c
static inline int16_t clamp_i16(int32_t v, int16_t lo, int16_t hi)
{
    if (v > hi) return hi;
    if (v < lo) return lo;
    return (int16_t)v;
}

#define CURRENT_MAX  16384   /* 电调允许的最大电流值（讲解时以战队实际电调为准） */

void send_current(int32_t raw_out)
{
    /* 输出限幅：先压范围再发送，杜绝溢出反转 */
    int16_t cmd = clamp_i16(raw_out, -CURRENT_MAX, CURRENT_MAX);
    can_send_motor_cmd(cmd);
}
```

- 限幅不只是「防止溢出」，还是**性能保护**：电流上限就是给电机和电调的「保险丝」。
- PID 的**积分项也要单独限幅**，否则限幅期间积分还在累积，会加重积分饱和（2.5 讲过）。

#### 输入合法性检查（Input Check）

传感器传来的数不一定都是真的。CAN 线松了、协议对错了、芯片坏了，都可能送来离谱的数据：转速 99999、角度 −32768、电压 0。**如果直接拿这些数去控制，输出就是灾难**。

**所有进入控制逻辑的输入，先问一句「这个数像真的吗」**：

```c
/* 输入合法性检查：超出物理范围的数据一律不信 */
static int16_t last_valid_rpm = 0;
static uint8_t bad_count = 0;

bool rpm_looks_valid(int16_t rpm)
{
    return (rpm > -30000 && rpm < 30000);   /* 物理上不可能超出 */
}

void control_loop(void)
{
    int16_t rpm = get_rpm_feedback();
    if (!rpm_looks_valid(rpm)) {
        rpm = last_valid_rpm;               /* 用上一次可信值顶上 */
        bad_count++;
    } else {
        last_valid_rpm = rpm;
        bad_count = 0;
    }
    if (bad_count > 50) {                   /* 连续 50ms 异常 → 传感器挂了 */
        send_current(0);                    /* 断电保护 */
    }
    /* ... 用 rpm 做速度闭环 ... */
}
```

> **一句话总结：输出出门前先压范围，输入进门时先验真假——不设限的代码等于把车钥匙交给一个疯子。**

### 概念四：通信中断（Communication Loss）—— 断联不是停机，是换策略

**先给结论：通信中断时，每个模块都要有自己「断联后的行为设计」：哪些继续、哪些降级、哪些停下。**

机器人的通信不止一条：CAN 总线（电机、传感器）、裁判系统串口、遥控器无线、上位机串口。它们各自断联的后果和处理策略都不一样。判断标准只有一条：**没了这条数据，我还能不能安全地干这件事？**

| 中断对象 | 还能安全干什么 | 不能干什么 | 典型策略 |
|---|---|---|---|
| 遥控器（DR16） | 无 | 一切 | 超时 100ms → 急停 |
| 某个电机 CAN 反馈 | 其他电机正常动 | 这个电机 | 该电机断电 + 报故障 |
| 裁判系统 | 运动、云台 | 射击（没有血量/功率数据） | 停射保运动，屏幕提示离线 |
| 上位机（视觉） | 底盘、云台手动 | 自动瞄准 | 降级为手动模式 |

设计要点：

- **提前想好「离线策略」**，而不是断联后让代码裸奔。比如裁判系统离线：规则上射击会无效，继续射击只会浪费弹丸——所以「停止射击、保留运动」是典型选择。
- **离线状态必须可观测**：车上的 LED、屏幕 UI 要能直接看出「谁离线了」，否则场上根本不知道发生了什么。
- **CAN 断线还有一个隐藏坑**：CAN 控制器在断线时会疯狂重发，错误计数器满了会进入 bus-off 状态，整条总线瘫痪。所以断线后要及时复位 CAN 控制器，别让它拖垮全车（2.6 电气篇讲过 CAN 拓扑，这里补上软件侧的处理）。

> **一句话总结：通信中断 ≠ 停机。提前设计好「谁继续、谁降级、谁停下」，断联时照表执行。**

### 概念五：电机掉线 —— 反馈沉默 = 最危险的状态

**先给结论：电机反馈突然不更新，比反馈数据错误更危险——因为「没消息」本身就是要命的坏消息。**

电机掉线通常来自：CAN 线松了、接插件氧化、电调死机。软件侧能观察到的现象只有一个：**CAN 反馈帧不再更新**（数据停在最后的值不动，或者根本收不到）。

危险在于：反馈停了，你的速度闭环还「以为」电机在转——误差不变，积分项持续累积，输出越推越大。等线重新接上，电机可能瞬间满功率狂转。

处理分两步：

1. **超时断电**：200ms 没收到该电机反馈，把它的电流直接置 0，同时把闭环里的积分清零。
2. **报障 + 重连**：故障状态上报到 UI/LED；恢复接收后，不能直接满血复活，要走「恢复流程」（见概念九）。

```c
/* 电机反馈超时：CAN 回调喂狗，控制周期检查 */
static uint32_t last_fb_tick[4] = {0};  /* 四个电机各自的喂狗时间 */
static bool     motor_alive[4] = {false, false, false, false};
static int16_t  motor_rpm[4]   = {0};   /* 保存最新转速，供闭环使用 */

void on_motor_feedback(uint8_t motor_id, int16_t rpm)
{
    last_fb_tick[motor_id] = now_tick;   /* 收到反馈 = 喂狗 */
    motor_alive[motor_id] = true;
    motor_rpm[motor_id] = rpm;           /* 存下最新转速 */
}

void motor_protect_check(void)
{
    for (uint8_t i = 0; i < 4; i++) {
        if ((uint32_t)(now_tick - last_fb_tick[i]) > 200u) {
            motor_alive[i] = false;
            send_current_to(i, 0);       /* 掉线电机断电 */
        }
    }
}
```

> **一句话总结：反馈沉默本身就是故障信号——超时就断电，重连要走恢复流程，绝不瞬间复活。**

### 概念六：传感器异常 —— 数不靠谱，闭环就离谱

**先给结论：传感器是控制器的「眼睛」。眼睛报假消息，比眼睛瞎了更危险。**

IMU 抽风、编码器乱跳、裁判系统血量为负数……传感器异常的常见原因：接线松动、供电不稳、电磁干扰、芯片静电损坏。它和「电机掉线」的区别是：**数据还在更新，但内容是错的**。

识别手段分三层，从轻到重：

| 手段 | 判断 | 处理 |
|---|---|---|
| 范围检查 | 读数超出物理极限（转速 99999） | 丢弃，用上次可信值 |
| 跳变检查 | 两次读数差太多（角度 1ms 跳 180°） | 丢弃或滤波 |
| 连续性检查 | 连续 N 次全异常 | 判定传感器故障 → 断电/降级 |

注意：**范围检查的边界要符合物理事实**，不能拍脑袋。比如编码器读数范围是 −32768~32767，但你车上的电机最快只能到 ±8000 RPM，那么 ±10000 以上的读数都可以直接判假。

```c
/* 跳变检查：角度类数据两次差太多 → 丢弃 */
#define ANGLE_MAX_STEP  1800    /* 1ms 内角度最多变 18°（0.01° 分辨率） */

static int16_t last_angle = 0;

bool angle_looks_valid(int16_t angle)
{
    int16_t diff = (int16_t)(angle - last_angle);
    if (diff > ANGLE_MAX_STEP || diff < -ANGLE_MAX_STEP) {
        return false;            /* 物理上不可能跳这么快 */
    }
    last_angle = angle;
    return true;
}
```

> **一句话总结：传感器数据进来先过三关：范围关、跳变关、连续关。宁可降级用旧值，不用离谱的新值。**

### 概念七：机械卡死（堵转）—— 电流飙升 + 转速为零 = 立刻断电

**先给结论：堵转是机械卡死最典型的信号：电流拉满、转速却≈0。它正在把电能全变成热能烧你的电机。**

云台撞到限位、轮子被卡住、摩擦轮挤死……机械卡死时，电机绕组还在承受大电流，但转子转不动——**所有电能都变成热量**，几秒钟就能把电机烫到手不能碰，几十秒就能烧毁线圈。

但「电流大」本身不能直接判堵转：正常加速爬坡时电流也大。真正的判据是**组合信号**：

```
电流 |大| 且 转速 |≈0| 且 持续 |超过500ms|  →  堵转 → 断电
```

三个条件缺一不可，最后一条最关键——瞬时的「大电流低转速」可能只是启动瞬间，持续才是卡死。

```c
/* 堵转检测：电流很大但转速≈0，且持续一段时间 → 断电保护 */
static uint32_t stall_ms = 0;

#define STALL_RPM       100      /* |转速| < 100 视为「没在转」 */
#define STALL_CURRENT   12000    /* |电流| > 12000 视为「在死顶」 */
#define STALL_TIME_MS   500u     /* 持续 500ms 才判定堵转 */

void stall_check(int16_t rpm, int16_t current)
{
    if ((rpm > -STALL_RPM && rpm < STALL_RPM) &&
        (current > STALL_CURRENT || current < -STALL_CURRENT)) {
        stall_ms++;                       /* 每 1ms 控制周期加一 */
    } else {
        stall_ms = 0;                     /* 不满足条件就清零，重新计时 */
    }
    if (stall_ms > STALL_TIME_MS) {
        send_current(0);                  /* 堵转 → 断电 */
        fault_led_on();                   /* 亮灯提示机械组来拆 */
    }
}
```

- 堵转保护触发后，**不要自动恢复**：机械卡死是物理问题，代码解决不了，必须人来看。
- 摩擦轮类「故意堵转」的机构要单独对待——它们正常工作时电流就很大，判据要用转速和持续时间区分。

> **一句话总结：电流大 + 转速零 + 持续超时 = 堵转。电能全在变热，第一时间断电，然后喊人。**

### 概念八：电源异常 —— 电压低了，先降档再报警

**先给结论：电池电压是整车的「体能条」。电压异常时要主动降档，而不是硬撑着把输出拉满。**

电源异常的两大主角：

#### 低电压检测

电池电压会随电量和负载波动：电量低时电压掉，突然大电流输出时电压也会瞬间塌下去。如果电压已经低到临界值还继续全功率输出，**主控会先断电重启**——场上直接「死机」，比降档可怕得多。

处理：分档降级。比如（具体阈值以战队电池和规则为准，讲解时结合实车数据）：

```
电压 > 24.0V   正常，全功率
电压 22~24V    降档：限功率、减加速度
电压 < 22.0V   保命：只留云台和基本运动，禁止射击，提示换电
```

#### 功率超限降档

RM 规则对底盘功率有限制（超功率会被裁判系统扣血）。当功率预算吃紧时，代码要**预测下一拍输出会超限，就先把自己的输出按比例压下去**，而不是等裁判系统判罚。这本质上也是一种「输出限幅」，只是上限由电压和功率预算动态决定：

```c
/* 功率保护：电压低时按比例降电流，简单线性降档 */
int16_t power_protect(int16_t cmd, int16_t vbat_mv)
{
    if (vbat_mv < 24000) {                    /* 24.0V 以下开始降档 */
        /* 22.0V 时降到 0：线性映射 */
        int32_t scale = (int32_t)(vbat_mv - 22000) * 100 / 2000;
        if (scale < 0)  scale = 0;
        if (scale > 100) scale = 100;
        cmd = (int16_t)((int32_t)cmd * scale / 100);
    }
    return cmd;
}
```

- 电压检测要**滤波**：瞬间压降（比如超电瞬间抽电流）不代表电池真没电，用短时间平均或滞回比较，避免保护抖来抖去。
- 低电压的**终极保险是硬件**：电源管理模块本身有保护，但软件侧不降档，硬件就会用「重启」教你做人。

> **一句话总结：电压是体能条——低电量先降档、再报警、最后保命。硬撑的代价是主控重启。**

### 概念九：缓启动（Ramp）—— 上电瞬间，别全功率冲出去

**先给结论：目标值突变时，让输出按固定斜率爬过去，而不是一步到位——这是对电流、机械和队友的三重保护。**

设想：开机自检刚结束，底盘目标从 0 直接变成 5000。PID 一看误差巨大，输出瞬间拉满——**电流冲击**（电池和电调突然承受最大电流）加上**机械冲击**（齿轮「啪」地一响），云台则可能猛地甩头。你见过哪个电机突然上电不抖一下的？这就是阶跃输入的代价。

缓启动（也叫斜坡函数 Ramp）做的事：**限制输出每周期最多变化多少**，让它按固定斜率爬到目标：

```c
/* 缓启动：输出按固定斜率逼近目标（每 1ms 调用一次） */
static int16_t out_now = 0;

#define RAMP_STEP   50      /* 每 1ms 最多变化 50 → 5000 用 100ms 爬满 */

void ramp_to(int16_t target)
{
    if (out_now < target) {
        out_now += RAMP_STEP;
        if (out_now > target) out_now = target;   /* 到顶后钉在目标上 */
    } else if (out_now > target) {
        out_now -= RAMP_STEP;
        if (out_now < target) out_now = target;
    }
    send_current(out_now);
}
```

```
阶跃输出：  电流 ████████|             （瞬间拉满：冲击！）
斜坡输出：  电流 ▁▂▃▄▅▆▇|             （平稳爬升：无冲击）
```

- 斜率的选择要平衡：太慢，车反应迟钝、被对手遛；太快，冲击保护形同虚设。底盘、云台、摩擦轮可以用不同的斜率。
- **升降双向都要 ramp**：急停其实也是一种「阶跃」，直接置 0 也有冲击——但对「安全停机」来说，快比稳更重要，超时急停可以直接置 0，正常减速才用斜坡。
- ramp 不是万能的：它解决「指令突变」，解决不了「负载突变」。真堵转了，该断电还是断电。

> **一句话总结：输出别跳崖，让它走坡道。上电缓启动，电流、齿轮和队友都感谢你。**

### 概念十：故障恢复设计 —— 保护触发之后，故事还没完

**先给结论：保护触发只是上半场，怎么恢复、让谁知道，才是可靠性设计的下半场。**

#### 保护状态要可观测

保护触发了，但没人知道，等于没保护。可观测性两件套：

- **LED 灯语**：不同故障用不同颜色/闪烁频率（比如：红灯常亮=堵转，红灯慢闪=通信断，黄灯=低电压）。上电后先亮一遍，也能顺便验证 LED 没坏。
- **日志**：故障类型 + 触发时间 + 关键数据（当时的电流、电压、误差）存下来。赛后复盘就靠它。串口打印要控制频率，别让日志把控制周期拖垮。

#### 恢复策略：按故障类型分

| 故障类型 | 恢复方式 | 原因 |
|---|---|---|
| 遥控器超时 | 数据恢复后自动恢复 | 无线电抖动是常态，自动恢复才不误事 |
| 电机 CAN 掉线 | 数据恢复后自动恢复，但积分清零 | 断联是偶发的，清积分防止「憋大招」 |
| 堵转 / 传感器连续异常 | 需人工确认（按键/裁判系统 UI 确认） | 物理问题代码解决不了，必须人来查 |
| 低电压 | 电压回升后自动恢复 | 电量是实时状态，没道理锁死 |

核心原则：**软故障（通信抖动）自动恢复，硬故障（机械/传感器损坏）人工确认。** 恢复时也走 ramp，别让车「诈尸式」弹起来。

用一个状态机统一管理：

```c
typedef enum {
    STATE_NORMAL = 0,   /* 正常控制 */
    STATE_PROTECT,      /* 保护中：输出切断，记录故障 */
    STATE_RECOVER       /* 恢复确认：等待人工解锁 */
} state_t;

static state_t state = STATE_NORMAL;

void fault_fsm_run(void)
{
    switch (state) {
    case STATE_NORMAL:
        if (any_fault()) {
            state = STATE_PROTECT;
            send_current(0);
            fault_log();
        }
        break;
    case STATE_PROTECT:
        if (no_fault() && need_manual_recover()) {
            state = STATE_RECOVER;          /* 等人工确认 */
        } else if (no_fault() && !need_manual_recover()) {
            state = STATE_NORMAL;           /* 软故障自动恢复 */
        }
        break;
    case STATE_RECOVER:
        if (user_confirmed()) {
            state = STATE_NORMAL;
        }
        break;
    default:
        state = STATE_NORMAL;
        break;
    }
}
```

> **一句话总结：保护要看得见（LED/日志），恢复要分轻重——软故障自动恢复，硬故障人工确认。**

### 概念十一：鲁棒性思维 —— 写代码时多问一句

**先给结论：可靠性不是「最后加的保护层」，而是写每一行代码时的思考习惯。**

把前面所有机制抽象成一句话，就是鲁棒性思维（Robustness）——**永远假设数据会出错、通信会中断、硬件会损坏，然后问自己：这一行代码在这三种情况下会怎样？**

写代码时的自检三连：

1. **如果这里收到的数是错的（离谱/过期/没有），会怎样？** → 加检查/超时/默认值
2. **如果这个函数被连续调用 10000 次，状态还正确吗？** → 检查边界、累加溢出、计数器回绕
3. **如果这段代码在比赛进行中被触发，车会安全吗？** → 默认输出永远是安全值（0），而不是任意值

好消息是：这套思维可以像肌肉一样练出来。练的方法就是本节的实践任务——**故意制造故障**（拔线、堵轮、关遥控器），看你的代码死不死。每次实车调试前先过一遍「故障注入」清单，比读十篇可靠性文章都管用。

> **一句话总结：可靠性不是补丁，是习惯。写每一行代码时多问一句「如果这里出错了会怎样」。**

### 任务一：给遥控器加 Timeout 急停

## 常见问题与排查

| 现象 | 可能原因 | 排查方法 |
|---|---|---|
| 超时保护频繁误触发 | 阈值太小 / 控制周期不稳定 | 日志看实际接收间隔，阈值取 3~5 倍 |
| 电机「诈尸」瞬间狂转 | 掉线期间积分累积，重连后释放 | 掉线时清零积分，恢复走 ramp |
| 堵转保护不触发 | 电流阈值太高 / 转速判据太宽 | 日志看堵转瞬间的电流转速，按实车改阈值 |
| 堵转保护误触发（正常爬坡也断电） | 持续时间太短 / 没区分爬坡 | 加长 STALL_TIME_MS，或加电流渐变判断 |
| 限幅后电机仍溢出反转 | 限幅加在错误的位置（发送函数外） | 确认最后一道关卡在 CAN 发送前 |
| 低电压保护抖动 | 电压采样没滤波 / 没加滞回 | 采样取短时平均，降档和恢复用不同阈值 |
| 恢复后车猛地一冲 | 恢复没走 ramp / 目标还停在旧值 | 恢复时目标先同步到当前值再 ramp |
| 急停也有冲击声 | 正常减速走了 ramp 太慢，被外力打断 | 安全停机直接置 0 是允许的，优先保安全 |
| 拔了一根 CAN 线，全车都不动了 | CAN 控制器进入 bus-off，总线被拖垮 | 掉线检测里复位 CAN 控制器，隔离故障节点 |
| 保护明明触发了，LED 却没反应 | 灯语写在保护逻辑外面 / LED 本身坏了 | 上电自检亮一遍灯，日志与灯语交叉验证 |

## 课后自测

1. 遥控器断联后，「保持最后指令」和「急停置 0」各有什么风险？为什么超时保护通常选后者？
2. 为什么说「电流大 + 转速 0」不能单独判堵转，还要加「持续 500ms」？举一个不加持续时间会误判的场景。
3. 裁判系统离线时，为什么建议「停止射击、保留运动」而不是整车急停？
4. `(uint32_t)(now_tick - last_tick) > 100` 和 `now_tick > last_tick + 100` 在时间戳回绕时有什么不同？
5. 写出一个「低电压自动恢复、堵转人工确认」的状态机转移表（当前状态 × 事件 → 下一状态）。
6. 你的车突然在场上所有电机全速正转，请列出至少 5 个可能原因，并说明每个原因对应的保护机制。
7. 看门狗（Watchdog）和「软件超时检查」有什么区别？为什么两者都要有？

<details><summary>参考答案</summary>

1. 保持最后指令：断联期间车继续按旧指令全速冲，撞车或出场地；急停置 0：损失本次操作，但车绝对安全。可靠性设计原则是「先保安全再保性能」，所以超时默认急停。
2. 启动瞬间、过小障碍瞬间都可能「电流大且转速低」，但它们会很快过去。只有持续超时才能区分「暂时受阻」和「真的卡死」，避免车一过小坎就断电。
3. 裁判系统离线只影响射击判定和状态反馈，运动和云台控制本身不依赖它。整车急停会让车在场上变成活靶子；保留运动能力，只砍掉「没裁判数据就无效」的射击，损失最小。
4. 时间戳（如 uint32 毫秒计数）溢出回绕后，`last_tick + 100` 可能溢出成小数，`now > last + 100` 会错误地判断「超时」；无符号减法 `(uint32_t)(now - last)` 在回绕时依然得到正确的时间差。
5. 例：

   | 当前状态 | 事件 | 下一状态 |
   |---|---|---|
   | 正常 | 任意故障 | 保护 |
   | 保护 | 故障消失且为软故障（电压低/遥控超时） | 正常 |
   | 保护 | 故障消失且为硬故障（堵转） | 恢复确认 |
   | 恢复确认 | 人工确认 | 正常 |

6. 例：CAN 总线受干扰发乱码被当成目标值（加协议校验/范围检查）；遥控器断联但代码保持最后指令（加超时急停）；PID 积分饱和后输出溢出反转（加输出/积分限幅）；传感器反馈乱码导致误差恒正（输入合法性检查）；恢复流程没清积分（恢复时清零+ramp）。
7. 软件超时检查只能抓住「数据没来」；硬件看门狗抓的是「整个程序都不动了」——比如死循环、中断风暴、内存踩踏，这时你的检查代码根本没机会执行。看门狗在程序挂死时强制复位 MCU，让车进入安全状态，是最后一道防线，所以两者都要有。
</details>
